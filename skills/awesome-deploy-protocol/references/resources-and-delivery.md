# 资源、配置与交付

## 额度与数据设计

开发参考基线：每应用所有服务合计内存上限 500 MiB、持久卷合计 50 MiB，共享存储池 64 GiB。MiB/GiB 为二进制单位，不是文件个数或单次上传限额。池容量不是单应用额度，也不是当前剩余容量承诺；实际目标配置可调整。

资源需逐服务显式填写。未填写时，解析器可能先继承同名旧服务设置，再默认 0.5 CPU / 500 MiB；两个服务都省略内存会超过 500 MiB。内存按实际占用消耗，声明值是硬上限，不是预先占满内存；达到上限可能被终止，不能依赖 swap 保证存活。声明通过仍不代表已获得部署时资源，活动版本、候选版本及未释放资源会影响准入。

只有服务端确需持久文件时才声明 storage：

```yaml
storage:
  name: data
  mountPath: /data
  sizeMiB: 50
  maxInodes: 10000
```

这是服务内部的字段片段，不是完整清单；完整声明模板见 assets/persistent-service.yaml。name 为小写字母起始的字母/数字/中划线，最多 31 字符；同一清单各服务不能共用同名存储。sizeMiB 和 maxInodes 必须是正整数，10000 只是示例申请，不是平台统一 inode 预算。每服务最多一个 /data 卷；多服务合计不得超过应用额度。

v2 存储要求目标服务器实际启用 XFS 硬配额；未启用时执行器拒绝，不能退回 v1 或取消卷声明规避。配额按实际分配的磁盘块和 inode 执行。SQLite 数据库、WAL/SHM、上传文件和其他持久内容都消耗额度；逻辑文件大小不能替代实际使用量。开发时处理写满、文件数用尽和写入中断，合理限制文件大小与保留量。不得用 /tmp 保存需要跨重建保留的数据。

新卷从空目录开始，平台负责创建受控目录并按运行身份配置访问权限；应用按自身启动逻辑初始化业务目录、表和数据。不能假定初始数据库已存在，也不要求容器以 root 运行或自行 chown 平台挂载；已有数据不得因每次启动而重新初始化或覆盖。

更新保留原服务及 storage.name、mountPath；不能通过删除/改名服务或卷、移动挂载来“完成迁移”。需要迁移时交由明确的数据迁移流程处理。浏览器 localStorage 属于浏览器站点数据，不需要服务器数据卷；变更域名、协议或端口可能影响原存档。

当前平台不提供通用业务数据自动备份恢复保证；根据需求明确备份责任和恢复流程，不将容器或部署记录当作业务备份。

## 配置与秘密

将数据库路径、非秘密 API 地址等配置映射到原程序真实读取的变量。仅仅声明 DATA_DIR/PORT 不会自动修改程序的存储或监听位置；开发新项目时实现对应读取，已有项目则使用它支持的配置项。

普通 env 值必须是单行字符串，不能与 secretRefs 同名。真实密码、Token、API Key、MASTER_KEY 不进入 Git、env 明文清单、build.args、前端脚本或镜像。可以交付无真值的配置说明或 .env.example，但平台不会自动读取仓库 .env 为运行配置，也不支持 YAML ${VAR} 插值。

确有业务需要时，用变量名引用平台秘密：

```yaml
secretRefs:
  MODEL_API_KEY: MODEL_API_KEY
```

平台配置对应值后，在运行时注入 MODEL_API_KEY；开发者不需要在 Git 预先生成密钥。外部 API Key 必须由供应商提供有效值，不能随机生成代替。MASTER_KEY 的自动生成与保存仅适用于平台约定的托管主密钥，需与应用原有格式和算法兼容；不能把所有带 KEY 的变量都当成自动生成，也不能擅自更换加密算法或已有主密钥。

无登录、无加密的静态网站不需要 BOOTSTRAP_PASSWORD/MASTER_KEY。确有业务登录时，用户名和初始化逻辑由业务应用决定；平台登录不替代业务登录。

## 交付检查表

1. 记录提交入口、目标仓库、ref/commit、最终部署名称及应用类型。区分部署名称 app.subdomain 与显示名称 app.name；记录部署名称由用户填写还是授权自动生成，并确保已向用户说明最终值。清单和部署入口必须一致，不能留下示例名称或未经说明的自动名称。当前社区固定 main，须确认目标代码与根目录清单、构建文件、全部静态资源和离线材料已一起推送到 main；其他分支的完整文件不能替代这项检查。直接使用支持 ref 的平台 API 时，才按实际请求版本核对。不要求额外提交压缩包。
2. 使用 schemaVersion: 2。核对实际入口、0.0.0.0、端口、健康路径、路由前缀、资源总量和必要配置；不根据模板猜出项目已有某个 API。
3. Dockerfile 属于支持语法，COPY 输入完整，基础镜像/业务镜像可获取；识别所有构建期网络依赖，不用“本机在线构建成功”替代离线条件验收。
4. 核对非 root、只读根、临时与持久目录、依赖可执行文件和运行网络。数据/秘密按实际需要声明，不为了检查增加业务功能。
5. 用项目自身测试验证真正业务；有真实 HTTP 检查时说明方法、地址/路径和结果。仅示例测试不能证明用户项目正确。
6. 清单、Schema、Dockerfile 策略、源码测试、受限容器运行、HTTPS 发布分别报告。未执行某层检查就标明未验证，不能将静态合规、queued、HTTP 202 或假探针当成真实上线。
7. 完整平台代码可用时，用该版本的 awesome_deploy.manifest.load_manifest 与目标 Settings 校验；官方 Schema 只是其中一层。普通开发者只有本包时可完成静态核对，不必取得部署 Token 或自行部署整套平台。
8. 发现不兼容时给出文件/字段、平台约束、证据及所需能力或决策。不能“为了通过”删除业务、篡改数据语义或把不支持组件改名。

建议将结果交付为四部分：已生成/修改文件；非秘密配置与依赖说明；已通过检查及证据；阻塞和未验证项。配置缺项不等于需要把秘密写回 Git。

## 维护与一致性

本包 assets/platform-profile.json 记录参考额度、源提交和执行规则文件摘要。维护者应在平台规则变化时同时复核规范、官方 Schema 快照及示例；仓库中的 tests/test_protocol_skill.py 会检测来源漂移，并用真实解析器与 Dockerfile 策略检查示例。

这些回归检查不等于实际镜像拉取、容器构建、OAuth、存储硬配额或公网发布验收。本包不自动执行生产操作；平台停服或入口不可达时仍可按规范开发，但不能声称当前能受理部署。
