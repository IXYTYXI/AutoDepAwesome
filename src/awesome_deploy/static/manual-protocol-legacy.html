1 协议目的、适用范围与业务红线

适配平台：Awesome Deploy 0.5.0；协议版本：v1.1；清单版本：schemaVersion: 1（无新增清单字段）；核对日期：2026-10-14；代码基线：5bf511306cc1031c7b1fadd814201265cf121b88。

本协议交给 AI 或开发者后，应产出随业务仓库一起提交的部署文件、明确的人工配置清单和可复核的验收记录。部署输入是目标仓库提交中的业务源码、根目录 awesome.yaml，以及该项目实际需要的 Dockerfile、.dockerignore、离线依赖等文件；无需下载或上传额外“交付包”。真实秘密值由管理员单独安全配置。目标是让平台按同一份已提交代码完成拉取、固定输入、构建、启动、健康检查、HTTPS 发布和版本验证。本文中的“必须”“禁止”是交付要求；“建议”是推荐做法。

业务红线：部署准备不得增加、删除或修改既有业务逻辑、功能、接口语义、权限认证、数据模型或依赖行为。只允许补充与既有行为一致的部署清单、容器封装、镜像引用和部署说明。镜像引用固定为摘要属于部署处理；不能借更换镜像替换业务实现。新项目按用户已经确认的业务需求开发，不能由本协议额外扩展需求。

若现有项目需要改业务代码才能适配，必须停止该适配，给出准确阻塞项及原因，等待业务方另行决定。不得通过删除数据库、关闭鉴权、伪造健康状态、替换为演示服务，或把客户端改写成 Web 服务来取得“部署成功”。本文的演示代码只用于全新测试仓库，不得覆盖用户项目。

2 交付流程与必需文件

先读取用户的真实项目、现有 Dockerfile、启动命令、依赖锁文件和配置说明；确认下表事实，再生成文件。不能从项目名称猜服务端架构，不能默认分支一定叫 main。未知事实标记“待确认”，有硬阻塞时交付阻塞报告，不得宣称可部署。

需要确认的输入

必须给出的事实

代码与版本

规范仓库 URL、真实分支/标签或完整 commit；源代码和部署文件必须在同一个将要部署的提交内

应用身份

新应用，或要更新的原 appId；期望域名前缀；是否沿用原应用的数据

运行结构

每个常驻 Web 服务的启动程序、容器端口、监听地址、工作目录、CPU/内存

访问与健康

公开路径指向哪个服务、服务原始路径、是否剥离前缀；既有可用健康检查方式

环境与存储

普通变量与秘密引用分开；真实写入目录、是否已有 /data 配置能力、历史数据兼容性

依赖与限制

构建依赖是否已离线准备；业务外部接口的真实域名、协议与端口、是否可通过公网 IPv4 TCP 443 访问、是否使用本业务自己的 API Key；运行是否依赖私网、其他端口的外部数据库、后台进程、root 或可写根目录

repository-root/
├── awesome.yaml          # 必须：平台唯一部署清单，必须在根目录
├── Dockerfile            # 使用 build 时必须；实际位置可由 build 指定
├── ...                   # 原项目业务代码、锁文件和必要构建产物
├── .dockerignore         # 建议：减少构建上下文，禁止排除必要文件
└── DEPLOYMENT.txt        # 本协议要求的人类/AI 交接说明；平台不解析此文件

每个服务必须二选一：build（仓库内构建）或 image（现成业务镜像）。image 模式不要求该服务的 Dockerfile，但仍必须有根目录 awesome.yaml；镜像必须确实包含目标业务版本，不能只用基础镜像冒充成品。多个服务可以复用 Dockerfile，但启动方式与实际服务行为必须分别明确。

DEPLOYMENT.txt 应写明：适配的协议/平台版本，仓库与 ref，服务启动命令，端口与路由，配置名称及用途，哪些秘密需管理员准备，持久数据路径与兼容要求，构建方法，验证命令/结果/未验证项，以及本次文件差异。不得记录密码、令牌、真实秘密值。Compose、Kubernetes 文件、.env 文件均不替代 awesome.yaml，平台不会自动读取它们完成部署。

3 仓库、版本与 YAML 规则

仓库 URL 必须是平台允许的 HTTPS Git 地址；默认主机为 github.com、gitlab.com。GitHub 使用 https://github.com/组织/仓库 或末尾 .git，不能使用 /tree/main、文件页面、下载包链接。禁止 URL 中夹带用户名、密码、令牌、端口、查询参数、片段、尾随斜杠或百分号编码；GitLab 子组路径可用，但主机必须获准。仓库重命名后使用最终规范地址，平台不会跟随 Git HTTP 重定向。

ref 必须为真实存在的字面分支、标签或完整提交哈希，最长 200 字符，格式为 [A-Za-z0-9][A-Za-z0-9._/-]{0,199}；不支持中文分支名，禁止 ..、//、尾部 / 或 .、以点开头或 .lock 结尾的路径段，也禁止 HEAD~1 等修订表达式。推荐以完整 commit 做验收。平台先解析并固定提交，执行期间不会因为分支变化自动换代码。尚未提交或尚未推送的本地文件不会参与部署。私有仓库须由管理员预先配置服务器读取授权，本机已经登录 GitHub 不代表服务器能读取。

源码导出不包含 .git；构建不能依赖 git describe 等读取 Git 元数据。源码不支持符号链接、Git 子模块或 .gitmodules 文件，不自动下载 Git LFS 对象。必要文件必须在目标提交中可取得；默认源码预算 256 MiB，文件/目录数量上限 100000，实际服务器配置可能更严。

awesome.yaml 必须为 UTF-8 普通文件、大小不超过 256 KiB。只接受单个 YAML 映射文档，所有映射键为字符串。禁止重复键、锚点、别名、显式 tag；嵌套最多 32 层，解析事件预算 10000。未知字段一律拒绝，不能扩展 x-*、ports、volumes、networks、deploy、privileged 等 Compose 字段。配置不做 ${VAR} 或宿主机环境变量插值。

API 单次请求体上限 128 KiB，因预检会把 YAML 放进 JSON 字符串，请保持清单远低于该限制。仓库文件可达 256 KiB 并不代表 256 KiB 的预检 JSON 请求可提交。

4 awesome.yaml 字段协议

字段

必填与精确要求

schemaVersion

必须是整数 1

app.name / app.description

均必填；name 为 1–100 字符字符串，description 为最多 2000 字符字符串，可以为空

app.subdomain

必填；1–7 位小写字母、数字或中划线，首尾必须为字母/数字；必须与控制台/API 提交前缀一致

services

必填对象，1–16 个服务；服务名匹配 ^[a-z][a-z0-9-]{0,30}$

services.<name>.kind

必填且只能为 web，不能把数据库或 worker 改名伪装成 web

image / build

必须且只能选择一个；image 为真实可拉取的镜像引用，最长 512 字符；build 见第 5 章

port

必填整数 1–65535，是容器内部实际 HTTP 监听端口；建议使用 8080 等非特权端口。宿主机端口由平台分配

healthcheck

必填；type 为 http 或 exec，详细条件见第 6 章

env

可选对象，最多 128 项；键符合 ^[A-Za-z_][A-Za-z0-9_]*$；值必须是单行字符串，最多 4096 字符；数字/布尔值也必须加引号

secretRefs

可选对象，最多 128 项；键是容器环境变量名，值是管理员配置的秘密名称；不能与 env 使用同一个键

command / entrypoint

可选字符串数组，各 1–128 项，每项最多 4096 字符；不是一整段 shell 文本。command 覆盖 CMD，entrypoint 覆盖入口程序。不要改变原有启动语义

workingDir

可选绝对容器路径，最长 512 字符，字符限字母/数字、/、_、.、-，禁止 .. 路径段；不因此获得写权限

resources.cpu / memoryMiB

可选；cpu 为 0.05–6 数值，memoryMiB 为 32–6144 整数，并同时受服务器设置与剩余总量约束

dependsOn

可选对象，键为同应用真实服务名，值为 started 或 healthy；禁止自环/循环/不存在的服务

storage

可选；只支持 name 与 mountPath: /data，见第 7 章

routes

必填数组，实际可执行范围 1–32 条；每条必须包含 path、match、service，stripPrefix 可选且默认 false

默认保留前缀：www、api、admin、auth、static、assets、mail、ftp、status；默认禁用包含 fuck 或 shit 子串的前缀，平台可另外配置。不要仅凭长度合法就认为可以使用；同名域名还必须空闲或属于要更新的原应用。

建议显式填写每个服务的资源。新服务缺省为 0.5 CPU / 512 MiB；更新时每个缺省资源字段优先继承同名旧服务。总量核算会包含仍存在的旧版本、候选版本和未确认清理的资源；不是每个应用各有 6 CPU。配置预检无法替代实际容量预留。

本协议采用解析器、执行器、网关的共同可执行范围。目前 JSON Schema 在三个位置更宽：routes 最多写了 128，但网关只接受 32；secretRefs 值允许点号/128 位，但秘密存储只接受第 7 章的 64 位格式；env 允许某些换行，但运行时只接受单行。必须遵守本文更严格的运行限制，不能只以 Schema 校验通过作为交付依据。

5 构建与容器运行约束

构建字段

要求

build.context

必填；相对仓库根目录，最简单是 .；不能为绝对路径，不能包含 ..、.git、反斜杠、空路径段或 ./ 子路径

build.dockerfile

必填；相对 context，指向实际普通文件；例如 context: backend 与 dockerfile: Dockerfile 对应 backend/Dockerfile。文件最大 256 KiB

build.target

可选；必须是 Dockerfile 中实际存在的阶段名称，最长 128 字符

build.args

可选；最多 128 项字符串参数，每值最多 4096 字符，不能携带秘密；禁止 BUILDKIT_*、BUILDX_*（忽略大小写）

部署服务器以 --network=none 执行构建 RUN。不能在部署时依赖 npm install、pip install、apt-get、curl 下载等在线网络操作。应由既有 CI/开发流程准备好包含依赖的业务镜像/依赖基础镜像，或将合法且适合目标 Linux 架构的离线依赖、编译产物提交入库。基础镜像由平台拉取并固定摘要；镜像仓库必须可达、有权限且可提供不可变摘要。不要复制 macOS 的 node_modules/虚拟环境到 Linux 冒充可用依赖。

Dockerfile 当前允许 FROM、RUN、COPY、ENV、WORKDIR、USER、EXPOSE、LABEL、CMD、ENTRYPOINT、ARG、STOPSIGNAL。每条指令写在一行；禁止反斜杠续行、heredoc、# syntax/# escape/# check 自定义指令、动态 FROM、FROM --platform、FROM 前 ARG、RUN --mount/--network 等 flags。COPY 只允许 --from=已定义的命名阶段，不能使用 --chown、--chmod、数字阶段或外部镜像来源。禁止 ADD、VOLUME、ONBUILD、HEALTHCHECK 等未支持指令。

镜像自身或基础镜像若声明了隐式 VOLUME、ONBUILD 也会被拒绝，不能只检查当前 Dockerfile。EXPOSE 不能替代清单 port，镜像 HEALTHCHECK 不能替代清单 healthcheck。需要改变文件属主时可在构建阶段使用普通 RUN chown，但不得在运行时要求 root 或对既有业务数据擅自递归改权。

运行环境为受控 Linux Rootless Docker。实际启动强制使用平台非 root 身份（默认 65532:65532），即使镜像写了其他 USER 也不能依赖它。根文件系统只读；/tmp 为 64 MiB 临时内存目录、noexec，/dev/shm 为 16 MiB；声明 storage 才有持久可写 /data。进程应前台常驻，不能靠后台化脚本立即退出；日志写 stdout/stderr，不要写 /var/log、/app 或 /root。

平台限制 128 个进程、nofile=1024、禁止提权并移除 capabilities。服务须适合该限制、目标服务器 CPU 架构和给定资源。应用监听 0.0.0.0:port，不能只绑定容器的 127.0.0.1。平台不会自动注入 PORT；只有项目本来支持该变量时才在 env 中填写。

构建成功后运行镜像按实际 image ID 固定。平台为固定基础镜像而生成暂存 Dockerfile，不代表获得修改用户业务代码的授权；不得自动安装缺失功能、改路由、删依赖或变更数据格式。

6 健康检查、网络与公开路由

HTTP 健康检查使用平台到容器的受管转发，GET 指定的容器原始路径，Host 为最终应用域名，HTTP 状态 200–399 为成功。路径最长 1024 字符、必须以 / 开头，字符限字母数字及 /_.~?=&%-；只使用现有可访问接口，不需要公网路由暴露同名路径。此检查不注入业务认证头；若现有接口必须认证，可使用已有可行的 exec 检查，不得关闭认证。不要用无条件 exit 0 假装健康。

healthcheck:
  type: http
  path: /healthz
  intervalSeconds: 10
  timeoutSeconds: 3
  retries: 3
  startPeriodSeconds: 30

也可使用 type: exec 与 command: ["程序", "参数"]，由镜像中已存在的程序运行并以退出码 0 表示健康。command 不隐式通过 shell 执行。无论采用何种方式，都应证明业务服务真正可用；没有现成健康路由不是授权新增业务接口的理由。

参数

默认与允许范围

intervalSeconds

默认 10；1–300 秒

timeoutSeconds

默认 3；1–60 秒，且不得大于 intervalSeconds

retries

默认 3；1–30 次，启动宽限期后计失败

startPeriodSeconds

默认 30；0–600 秒，但仍受执行器整体健康检查时限约束

intervalSeconds、timeoutSeconds、retries、startPeriodSeconds 都必须为整数。

默认一轮健康检查总时限为 180 秒，多个服务共享本轮截止时间；把 startPeriodSeconds 写成 600 并不能延长这个平台时限。较慢启动的应用应事先核实服务器配置，不能靠反复重试掩盖无法达到的启动时间。

Awesome Deploy 0.5.0 启用 public-https-v1 固定运行策略后，新提交的部署可由业务容器直接访问公网 IPv4 TCP 443，例如提供 HTTPS 接口的模型 API、对象存储和支付服务。现有内部依赖网络及宿主机隔离保留；平台不注入业务 HTTP 代理，也不要求重写现有 SDK 或业务调用方式。该策略按地址与端口限制连接，不按域名白名单放行，也不替业务校验 TLS 证书；业务客户端仍须正常验证 HTTPS 证书。

域名解析由平台配置，指定公共 DNS 为 223.5.5.5 与 1.1.1.1，只允许向这两个地址使用 UDP/TCP 53。宿主机全部已登记 IPv4 地址（含云公网 NAT 地址）、私网、环回、链路本地/元数据、保留地址、IPv6 和其他外联端口均被阻断。业务目标必须实际提供可达的公网 IPv4 TCP 443；需要 IPv6、私网数据库、HTTP 80 或其他端口的依赖仍是能力阻塞，不得换成本地假实现。

网络策略由平台配置并随任务输入冻结，schemaVersion 仍为 1，awesome.yaml 不新增 egress、代理、DNS、网络模式或其他放行字段。平台升级不会改写旧任务：旧冻结任务和原有应用维持内部网络；需要公网出站时，须在管理员启用并验收新策略后重新提交部署，重试原冻结任务不会获得新策略。

运行时出站放行不改变构建限制。构建 RUN 仍使用 --network=none；npm install、pip install、apt-get 等在线安装仍须在既有 CI/开发流程中准备完成，不能借运行时联网能力绕过离线构建要求。

同应用服务间有 dependsOn 边时，平台建立对应内部通信网络，使用服务名与容器端口通信，例如 http://api:8080。started 只等待进程启动，healthy 会等待依赖健康；它们也决定网络连接，不能假设没有依赖声明的服务自动互通。此连接是双向网络连通，不是 HTTP 权限控制。浏览器不能解析容器服务名：浏览器调用同域公开路径，如 /abc，而不是 http://api:8080。

路由 path 最长 512 字符，必须是以 / 开头的字面规范路径，字符限 /、字母数字、_、.、~、-；禁止正则、查询串、双斜杠、. 或 .. 路径段，不能占用 /.well-known/acme-challenge 或其子路径。相同规范路径与 match 组合不能重复；service 必须存在。match: exact 只匹配完整路径；prefix: /api 匹配 /api 及 /api/...，不会匹配 /apix，较长前缀优先，精确匹配优先。

访问路径与路由

容器收到的路径

path: /api，match: prefix，stripPrefix: false；GET /api/users

/api/users

path: /api，match: prefix，stripPrefix: true；GET /api/users

/users

path: /，match: prefix，stripPrefix: false；GET /abc

/abc

建议前缀路径除 / 外不写尾部 /，避免 /api 与 /api/ 的入口差异。stripPrefix 只处理上游请求路径，不会替你修正 HTML 静态资源链接、前端 base path、接口 URL 或重定向。应匹配原业务现有路径能力；不能通过改业务代码偷偷适配。

网关发布后会对每条路由发起 HTTPS GET 探测，并确认请求确实到达候选服务。prefix 路由可能探测随机子路径；2xx–4xx 可用于路由验证，未知路径正确返回 404 可以通过，持续 5xx 不行。精确路由会 GET 其精确路径，业务 GET 必须无破坏性副作用。路由验证只证明发布链路，不代替登录、上传、外部 API 调用等真实业务验收。

0.5.0 新发布的 Nginx 业务路由关闭响应缓冲（proxy_buffering off），读取上游响应的空闲超时为 300 秒，即相邻上游数据读取之间允许的最长等待时间，不是请求总时长。业务原有流式响应可及时传给浏览器；平台不会把非流式接口自动改成流式接口，业务 SDK/客户端自身的超时仍需按项目既有配置核实。已有路由不会因平台升级自动重写，重新发布后才应用新参数。不要据此承诺 WebSocket、无限长连接、上传体积或由清单自由调节网关超时。

7 秘密配置与持久数据

普通配置放 env；密码、访问令牌、API Key 等只写 secretRefs 引用，真实值由管理员安全输入。不要把值放仓库、.env、Dockerfile、build.args、image URL、部署请求或验收日志。秘密名称采用 ^[A-Za-z][A-Za-z0-9_-]{0,63}$（1–64 位，首位字母，不含点）。值必须是非空单行字符串，不能含换行/回车/NUL，存储上限 16 KiB。

调用外部模型或其他业务 API 必须配置该业务自己的有效 Key，并用 secretRefs 映射到项目原本读取的环境变量名；不需要改写 SDK。平台诊断 AI 的 Key 属于平台自身，不能借用、复制或默认注入业务容器。公网出站能力不包含供应商账号、额度或访问权限，不能因网络可达就宣称业务调用已经验收。

# 放在实际服务下；左边是容器变量名，右边是平台配置名称
secretRefs:
  UPLOAD_TOKEN: UPLOAD_TOKEN
# 由服务器管理员执行；会交互询问秘密值，不要把值写在参数中
/opt/awesome-deploy/.venv/bin/awesome-deploy --config /etc/awesome-deploy/config.json secret-set --repository https://github.com/your-org/your-repo --subdomain demo --name UPLOAD_TOKEN

秘密按规范化仓库 URL + 域名前缀定位，并在任务中固定具体版本。选对 appId、换域名、轮换秘密是不同事情：域名前缀改变后不得自动继承原前缀秘密；新应用不得自动继承同仓库/同前缀的其他应用秘密。要沿用原数据/配置，应选择原应用，管理员确认对应空间和版本可用。没有实际需要的秘密就不应凭空添加 UPLOAD_TOKEN 或任何访问令牌。

自 0.4.1 起保留的历史兼容边界：若同一仓库/前缀曾被多个应用使用，原应用仅可重用它自己在相同空间成功部署并实际引用过的相同秘密名称与版本。失败/冻结记录不算授权，尚未成功使用的新轮换版本不能借此继承；必须由管理员处理隔离冲突，不能自动复制别人的秘密或回退秘密版本。0.5.0 的公网出站能力不放宽该秘密归属规则。

# 可选：放在需要持久数据的真实服务下
storage:
  name: images
  mountPath: /data

每服务最多一个 storage；name 与服务名采用同样的 1–31 位命名格式，应用内不能共享 storage.name。卷由平台根据 appId、服务名、storage.name 建立归属，不接受用户指定 Docker 卷名。应用必须已有把持久文件写到 /data 的配置能力；仅声明 storage 不会把它原本写到其他目录的数据搬进来。

镜像必须预先建立 /data，并让实际运行 UID/GID 可写。默认身份的封装示例为 RUN mkdir -p /data && chown 65532:65532 /data；它只能用于准备镜像内新目录，不能作为修改业务文件或迁移历史数据的替代。不要使用 Dockerfile VOLUME /data。

包含持久服务的更新采用 recreate，候选镜像准备好后停止整个旧应用版本再启动新版本，存在停机窗口。已有成功版本的 storage 不得删除、更名或移动，也不能通过改服务名绕过。回滚镜像和路由不会回滚已经写入的数据；新旧版本必须兼容同一份数据，不支持自动迁移/恢复备份。卷缺失或身份不匹配应失败，不能悄悄创建空卷冒充原数据。

8 可以复制验证的最小参考

下面三个文件组成一个独立测试仓库，仅验证单 Web 服务部署链路，不是业务项目替代实现。使用时把文件直接放仓库根目录，选择空闲前缀，并保持 app.subdomain 与提交值一致；基础镜像仍需目标服务器能够拉取。本参考不需要真实秘密、联网安装依赖或持久卷。

schemaVersion: 1
app:
  name: 演示网页
  description: 单服务网页和同域名 API
  subdomain: demo
services:
  web:
    kind: web
    build:
      context: .
      dockerfile: Dockerfile
    port: 8080
    env:
      PORT: "8080"
    resources:
      cpu: 0.5
      memoryMiB: 128
    healthcheck:
      type: http
      path: /healthz
routes:
  - path: /
    match: prefix
    service: web
    stripPrefix: false
FROM python:3.12-slim
WORKDIR /app
COPY server.py /app/server.py
USER 65532:65532
EXPOSE 8080
CMD ["python", "-u", "/app/server.py"]
import json
import os
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import urlsplit


class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        path = urlsplit(self.path).path
        if path == "/healthz":
            payload, kind = b"ok", "text/plain"
        elif path == "/abc":
            payload, kind = json.dumps({"message": "Hello from Awesome API"}).encode(), "application/json"
        elif path == "/":
            payload = '<!doctype html><html lang="zh-CN"><meta charset="utf-8"><title>Awesome demo</title><h1>部署成功</h1><p>这个页面由仓库代码构建并通过 HTTPS 发布。</p><a href="/abc">查看同域名 API</a></html>'.encode()
            kind = "text/html; charset=utf-8"
        else:
            self.send_error(404)
            return
        self.send_response(200)
        self.send_header("Content-Type", kind)
        self.send_header("Cache-Control", "no-store")
        self.send_header("Content-Length", str(len(payload)))
        self.end_headers()
        self.wfile.write(payload)


if __name__ == "__main__":
    ThreadingHTTPServer(("0.0.0.0", int(os.getenv("PORT", "8080"))), Handler).serve_forever()

如果业务已是前端 + API 两个 HTTP 服务，可参考平台源码中的 examples/frontend-api 完整示例；示例仅帮助理解结构，不是部署所需的额外包，也不能覆盖现有业务项目。两个容器可以都监听 8080，宿主机端口由平台分别分配；同域 / 路由指向 web，/abc 路由指向 api 并 stripPrefix: true。该演示由浏览器经过同域路由调用 API，故无需添加服务间网络依赖；如果真实 web 容器要直接调用 api，则再声明 dependsOn。

# 实际 web 服务需在容器内调用 api 时，放在 web 配置下：
dependsOn:
  api: healthy
# 仅当真实程序已支持此配置变量，才添加对应 env：
env:
  API_BASE_URL: "http://api:8080"

这些片段不是独立 awesome.yaml；不能原样提交只有片段的文件。image 模式应以真实业务镜像替换服务的 build，保留 kind、port、healthcheck、routes 等必要字段。不得提交 registry.example、YOUR_IMAGE、待填写端口或伪造 sha256 值作为已就绪配置。

9 预检、提交与验收方法

建议按“静态核对 → 本地构建/运行 → 平台预检 → 推送目标提交 → 授权提交部署 → 真实业务验收”的顺序执行。仅生成文件不等于已经获准上线。测试需要用适当的独立环境；不要擅自下线正在使用的业务应用。

本地 Docker 测试至少复现 --network=none 构建、非 root 身份、只读根文件系统和临时目录限制，并检查真实业务监听与健康接口。普通 docker run 成功不能证明平台兼容；完整网络隔离、镜像冻结、秘密/存储归属及网关发布由平台执行验证。持久项目还要验证重新创建服务后原数据仍可读、新旧版本兼容。

历史示例提示：紧接着的 Basic 预检命令属于 0.5.0 基线，在当前飞书登录模式下不能直接使用。当前脚本/CI 部署请使用本节后面的 Bearer POST 示例。

# 管理员入口示例；只写用户名，curl 会安全询问密码
curl --user operator --fail-with-body --output awesome-v1.current.json https://awesome.guanghexinzhi.cn/api/v1/schema
curl --user operator --fail-with-body https://awesome.guanghexinzhi.cn/api/v1/capabilities

# 在业务仓库根目录生成预检请求，不包含真实秘密
python3 - <<'PYCODE'
import json
from pathlib import Path
Path("preflight.json").write_text(json.dumps({"manifest": Path("awesome.yaml").read_text(encoding="utf-8")}, ensure_ascii=False), encoding="utf-8")
PYCODE
curl --user operator --fail-with-body -H 'Content-Type: application/json' --data-binary @preflight.json https://awesome.guanghexinzhi.cn/api/v1/preflight

预检返回 scope: configuration_only 只代表清单校验；不会拉仓库、检查 Dockerfile、拉镜像、检查秘密存在与归属、检查真实数据兼容，也不预留域名、端口或容量。本文 0.5.0 基线曾使用 HTTPS 与运维 HTTP Basic；当前线上平台已启用飞书登录，下面的现行自动化接口使用独立的 Bearer 凭证，不能用 Basic、网页登录 Cookie 或 GitHub/GitLab 仓库凭证代替。

现行请求方法：使用 POST /api/v1/automation/deployments 提交 JSON 部署请求，携带 Authorization: Bearer、Content-Type: application/json 与 Idempotency-Key。HTTP 202 只表示任务入队。随后使用同一凭证调用 GET /api/v1/automation/deployments/{id} 查询任务结果；GET 不提交新部署。凭证获取、请求范围和重试规则见 自动化部署 API 使用手册。

{
  "repository": "https://github.com/your-org/your-repo",
  "ref": "main",
  "subdomain": "demo"
}

更新已有应用时，在请求中增加 "appId": "原应用ID"。已经绑定域名的应用必须保持原仓库和原前缀；下线后，原 appId 可以对同一原仓库重新认领空闲前缀，数据仍属于原应用。新建应用是独立身份，不能用“前缀一样”代替 appId，也不能因此拿到原数据卷。

# 每次新的部署使用新的 Idempotency-Key；凭证从安全配置注入
curl --request POST --fail-with-body -sS \
  -H "Authorization: Bearer ${AWESOME_DEPLOY_TOKEN}" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-initial-001' \
  --data-binary @deployment.json \
  https://awesome.guanghexinzhi.cn/api/v1/automation/deployments

# 用提交响应中的 id 替换 JOB_ID，同一凭证查询结果
curl --request GET --fail-with-body -sS \
  -H "Authorization: Bearer ${AWESOME_DEPLOY_TOKEN}" \
  https://awesome.guanghexinzhi.cn/api/v1/automation/deployments/JOB_ID

提交返回 HTTP 202 只是入队。Idempotency-Key 必须为 1–128 位字母数字或 . _ : -；网络响应丢失可用相同键与相同请求取回同一任务，同键不同内容会冲突。为修正代码/配置发起新部署必须换键。任务应观察到 succeeded，并确认结果 URL、固定 commit、路由与业务功能；历史 succeeded 不代表此刻仍在线，当前状态看应用管理。

3. 不得增加、删除或修改既有业务逻辑、功能、鉴权、接口语义、数据模型或依赖行为。不得关闭认证、伪造健康结果、用示例程序替换项目、擅自将客户端改写为服务端。若必须改业务才能部署，停止该适配，解释原因，不得偷偷改代码。
4. 在保留业务行为的前提下，只生成必要的 awesome.yaml、Dockerfile/镜像引用、.dockerignore 和 DEPLOYMENT.txt；不需要的配置、秘密、数据卷不要添加。构建文件也不能通过换入口或排除文件删掉业务功能。awesome.yaml 不得添加 egress、DNS、代理或网络模式字段。
5. 文件必须完整且可复制，写明仓库内路径；awesome.yaml 放仓库根目录。每服务 image/build 二选一；遵守协议比 Schema 更严格的路由/秘密名/单行环境变量限制。不得虚构镜像摘要、秘密值、可用域名、appId 或测试结果。旧冻结任务维持内部网络，需要公网访问时应重新提交部署，不是重试旧任务。
6. 输出真实 diff，逐项解释为什么只涉及部署封装。列出管理员需配置的业务自有秘密名称、Git/镜像拉取前提和待确认项，不输出秘密值，不借用平台诊断 AI Key。secretRefs 使用项目原有环境变量名。
7. 运行可执行的静态校验及适当本地验证，记录命令、结果、未执行项。预检通过只记为配置通过；实际发布必须在用户授权提交后，以 succeeded、真实外部 API 调用和业务验收确认。流式业务应实测数据逐段到达；新路由关闭响应缓冲，300 秒是相邻上游数据读取的空闲超时，不是无限等待保证。没有权限、Docker、业务 Key 或网络时，明确写未验证。
8. 最终交付：兼容性结论、仓库文件树与完整文件、部署参数、操作员准备清单、验证记录、业务未改动说明、所有剩余阻塞。无需额外 ZIP。若有阻塞，不得宣称“可直接上线”。提交、推送和真实部署按用户授权执行；仅生成协议文件不构成发布授权。

如果 AI 无法读取飞书链接，请把本协议正文与上方执行指令直接复制给它，并提供它能够读取的真实仓库或工作目录；不需要下载、上传额外交付包。真正需要进入部署提交的是项目源码和本协议规定的仓库文件，秘密值不需要交给 AI。

12 交付验收清单与依据

□ 已识别真实业务架构，没有修改既有业务功能/逻辑，也没有新增无必要的令牌、接口或后台功能。 □ 同一目标提交包含根目录 awesome.yaml、实际 Dockerfile/镜像、业务源码和全部离线构建材料，且已经按授权提交/推送。 □ 应用身份、仓库、ref、前缀核实一致；更新使用原 appId，数据与秘密归属没有混用。 □ 清单通过当前平台预检；同时核查了 Schema 未覆盖的 Dockerfile、路由上限、秘密名称、单行 env、历史存储等执行限制。 □ 构建可在无网络下完成；镜像适配服务器架构，不含隐式 VOLUME 或 ONBUILD。 □ 服务在非 root、只读根目录、限定资源下前台运行并监听 0.0.0.0；不依赖不支持的后台/数据库能力。需要外部 API 时，已核实公网 IPv4 TCP 443 和平台指定 DNS 可满足真实依赖，没有私网、宿主机、元数据、IPv6 或其他端口要求。 □ 业务外部 API 使用自己的有效 Key，经 secretRefs 配置；未借用平台诊断 AI Key。需要公网能力的旧应用已重新提交部署；真实 API 调用与所需流式行为已有验收记录，未执行项明确标记未验证。 □ 健康检查针对真实服务且可成功；路由、前缀、浏览器访问及公开探测路径行为与原项目一致。 □ 所需秘密已由管理员安全配置；仓库、文档、命令参数和日志没有真实秘密值。 □ 若使用持久化，应用确实写入 /data，实际 UID/GID 可写，更新/回滚的数据兼容性和保留行为已确认。 □ 已记录实际执行与未执行的测试；真实上线验收包含 succeeded、固定 commit、公开 URL 及原业务关键功能，而非只有首页截图。

本协议以已上线的 0.5.0 实现与验收边界为依据。协议维护者应在平台升级时同步核对字段、运行约束、示例和测试，不得把尚未上线的规划写成承诺。清单仍采用 schemaVersion 1；历史 ZIP 保留 0.4.1 的 JSON Schema、原仓库示例及当时记录，不是当前部署输入或 0.5.0 验收证据。遇到文档与实现冲突，应暂停宣称兼容、记录冲突并由平台维护者修订，不允许 AI 自行放宽限制。

历史附件的 VALIDATION.json 记录的是 0.4.1 时两个示例的静态检查：清单语义、Dockerfile 语法、网关参数/配置生成及 Python 语法；当时未执行镜像拉取、Docker 构建/容器启动、真实 HTTPS 发布或业务功能验收。该记录不证明 0.5.0 的公网出站、业务 Key、外部模型调用或流式业务已经验收。使用本协议部署任何真实项目，仍须按第 9 章记录该项目实际执行的验证及未验证项；不要求取得或上传历史 ZIP。
