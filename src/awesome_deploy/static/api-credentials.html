03

API 调用指南

从创建凭证到确认部署结果，按以下步骤操作。

  1. 在左侧创建个人凭证，只显示一次完整值；放入调用方的密钥配置，设置为环境变量 AWESOME_DEPLOY_TOKEN。
  2. 准备部署请求 JSON，使用 Bearer 凭证和每次新部署独有的 Idempotency-Key 提交。
  3. 保存响应中的 id，用同一凭证查询任务，直到状态结束。

1. 首次部署

在调用程序的工作目录创建 deployment.json：

{
  "repository": "https://github.com/your-org/your-repo.git",
  "ref": "main",
  "subdomain": "demo"
}

将仓库、分支和域名前缀换成真实值；仓库内需要符合平台协议的 awesome.yaml。

2. 提交任务

先由 CI 或运行环境注入 AWESOME_DEPLOY_TOKEN，不要把凭证写进仓库或请求文件。

curl --fail-with-body -sS \
  -H "Authorization: Bearer ${AWESOME_DEPLOY_TOKEN}" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-initial-001' \
  --data-binary @deployment.json \
  https://awesome.guanghexinzhi.cn/api/v1/automation/deployments

202 只表示任务已入队；响应中的 id 是任务编号，不代表部署成功。

3. 查询结果

curl --fail-with-body -sS \
  -H "Authorization: Bearer ${AWESOME_DEPLOY_TOKEN}" \
  https://awesome.guanghexinzhi.cn/api/v1/automation/deployments/JOB_ID

把 JOB_ID 换成提交响应的 id。状态可能是 queued、running、succeeded、failed 或 recovery_required；仅 succeeded 表示该次部署成功。可结合响应中的 active 和 url 确认当前是否在线。

更新已有应用

在请求 JSON 中增加已有应用的 appId，保持仓库地址和域名前缀与该应用一致，并使用新的幂等键：

{
  "repository": "https://github.com/your-org/your-repo.git",
  "ref": "main",
  "subdomain": "demo",
  "appId": "已有应用编号"
}

单应用凭证只能更新指定应用。若创建新应用，不要填写 appId。

重试与权限

响应丢失时，用相同幂等键和完全相同的请求安全重试；新的部署必须换键，同键不同请求会冲突。凭证只能提交部署、查询它创建的任务，不能管理密钥、成员或下线。401 表示凭证无效或过期，403 通常表示没有目标应用的部署权限。

凭证只用于提交部署和查询该凭证创建的任务，不能管理密钥、成员或下线。

撤销个人凭证

撤销后，调用方不能再提交或查询，尚未执行的关联任务也会失去授权。
