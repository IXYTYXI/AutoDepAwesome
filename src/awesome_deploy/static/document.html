快速上手

  1. 准备仓库。把 awesome.yaml 放在仓库根目录；使用源码构建时，同时提交 Dockerfile 和构建所需文件。提交并推送到准备部署的分支。
  2. 填写部署信息。在部署控制台选择「创建新应用」，填写仓库地址、分支或提交版本、域名前缀。前缀须与清单一致。
  3. 补充应用配置。如页面提示缺少配置，在页面填写登录密码或供应商 API Key；托管主密钥由平台生成并保存。
  4. 等待实际验证。提交后可查看排队、构建、健康检查和 HTTPS 发布进度；显示「部署成功」后打开应用。
  5. 后续管理。在应用管理查看状态、管理密钥或下线。更新已有应用时，选择原应用以沿用身份和数据。

无需额外上传 ZIP「交付包」。平台从 GitHub / GitLab 拉取你已经提交的代码和部署文件。

多个服务按应用合计。内存按需使用，上述数值是上限，不固定预占。存储写满后会拒绝继续写入，内存超限可能终止服务。共享池不是单个应用可用的空间。

支持 HTTP Web 服务、网页与 API 路径分流，以及每服务一个 /data 持久存储。新建持久存储使用 schemaVersion: 2，声明容量和文件数量上限。

运行网络能力正在读取；部署前请确认是否允许调用外部模型 API。

构建命令默认无法访问网络，依赖需在基础镜像或构建上下文中准备好。平台保留正常构建缓存。

暂未提供：审批流、业务后台 worker、独立数据库服务、数据库迁移和自动备份。

部署技术协议

业务逻辑保持原样。部署准备可以补充清单、容器封装和镜像引用；不能增加、删除或修改用户的业务逻辑。无法部署时说明原因，不通过改业务功能取得部署成功。

文件 / 配置放在哪里必须满足
awesome.yaml仓库根目录UTF-8，最多 256 KiB。声明 app、services、routes；表单域名前缀与 app.subdomain 一致。
Dockerfile 与构建文件清单 build 指定的位置保留原业务行为；构建时不依赖外网。每服务在 build 与 image 中二选一。
端口与健康检查services 中监听 0.0.0.0，实际端口一致；检查路径或 exec 命令真实可用。
持久存储services 中的 storage挂载点固定 /data；v2 必填 sizeMiB、maxInodes。XFS 新存储从空目录开始。
密码和密钥平台补充配置表单Git 里只放 secretRefs 引用名，不提交实际密码、API Key 或主密钥。

运行环境为非 root 用户、只读根文件系统。应用需按原有逻辑把持久文件写到声明的 /data，临时文件写到允许的临时目录。桌面客户端不能直接作为 Web 服务部署。

清单结构示例

示例仅演示文件结构，不提供或替换业务实现。Dockerfile、端口、健康路径及资源申请须按实际项目填写；无需持久数据时省略 storage。

schemaVersion: 2
app:
  name: 示例应用
  description: HTTP Web 服务
  subdomain: demo
services:
  web:
    kind: web
    build:
      context: .
      dockerfile: Dockerfile
    port: 8080
    resources:
      cpu: 0.5
      memoryMiB: 128
    healthcheck:
      type: http
      path: /healthz
    storage:
      name: appdata
      mountPath: /data
      sizeMiB: 50
      maxInodes: 10000
routes:
  - path: /
    match: prefix
    service: web
    stripPrefix: false

密码与密钥

  • 应用登录密码：由你在部署配置表单中设置。初始用户名由业务应用决定，不是平台统一生成。
  • 外部 API Key：填写模型或服务供应商给出的真实值，随机字符串无法代替。
  • 托管 MASTER_KEY：平台识别后自动生成、加密保存并复用，不要求你先生成、写进 Git 或勾选「已保存」。其他名称的密钥不能一概视为自动托管。

已保存的密钥不在页面回显。应用管理中可查看名称、版本和状态，并对普通运行密钥进行轮换或吊销；主密钥不支持普通轮换。平台内吊销不会替你撤销外部供应商的凭据。

控制台使用飞书登录，业务应用仍按自身的登录逻辑运行。两者的账号和密码不是一回事。

更新与下线

更新、下线后重新部署时，选择原应用。保留数据的应用继续使用原数据与配置；不要为了重试创建另一个应用身份。

选项处理结果
保留数据保留平台受控业务文件、数据库及该应用保存的密码和密钥，供再次部署继续使用。
删除数据清除平台受控业务数据和该应用保存的密码、API Key、密钥，不可恢复。外部数据库不会自动删除。

下线及清理确认完成后释放域名和运行端口。源码、部署历史和构建缓存不因数据选项被删除。

有持久存储的更新可能短暂停机。版本回退不会撤销新版本已经写入的数据，更新前应确认数据格式兼容。

常见问题

获取代码失败或超时，先查什么？

确认仓库地址、分支或提交存在，私有仓库有读取权限；再检查平台到 GitHub / GitLab 的网络和代理。此阶段尚未构建业务服务，反复修改应用密码通常无助于解决拉取失败。

缺少秘密配置，需要去服务器找文件吗？

不需要。查看当前进度中的补充配置表单，填写项目登录密码或供应商 API Key，再保存并继续。不要把这些实际值提交到 Git。

健康检查失败，应该改什么？

按具体错误检查启动结果、监听地址、端口、健康路径、非 root 和只读文件系统要求。若必须改变业务代码，先明确原因再由业务方决定；不要伪造健康结果。

部署失败，域名和端口一定已经释放了吗？

不一定。新部署在分配资源前失败时可能尚未占用；已分配资源须确认清理完成才释放。更新失败也可能保留旧版本的资源。以应用管理中的当前状态为准，待恢复时不要假定资源已可复用。

应用会自动登记到飞书多维表格吗？

已支持。应用和部署记录由独立进程同步到专用多维表格；平台数据库仍是唯一权威，密钥和原始日志不会上传。打开应用登记表 ↗
