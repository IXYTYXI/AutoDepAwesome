同组网页项目接入 Awesome Deploy API｜后端实施手册

适用对象：同组网页项目的开发者及协助开发的 AI。核对日期：2026-10-23。本文描述当前已经上线的接口与调用方需要实现的部分；完整平台协议见文末链接。

先记住两件事：浏览器不得持有平台 Token，也不能从其他网页域名直接调用当前自动化接口。HTTP 202 仅表示部署任务已入队，不表示应用上线成功。

1. 接入边界与数据流

推荐链路：同组网页的已登录用户 → 该项目后端 → Awesome Deploy 自动化 API → 平台部署队列。网页只调用自己的后端；后端负责自身用户授权、持久化请求、保存平台任务编号和轮询结果。平台 Token 只放在该后端的密钥配置中。

当前自动化接口拒绝来自其他网页 Origin 的浏览器请求，即使浏览器携带 Bearer Token 也不能作为接入方案。如果对方项目只有静态页面，应先增加受控后端；不要将 Token 放入 JavaScript、页面配置、前端构建变量或浏览器存储。

2. 接入前准备

  1. 确定调用来源名称和负责的飞书成员；该成员须已登录平台并拥有目标应用的部署权限。
  2. 确定范围：需要创建多个新应用并更新负责人有权部署的应用时，签发 --all-apps 来源凭证；只更新一个已有应用时用 --app-id。同一来源凭证可多次提交，没有“只能部署一次或一个应用”的产品数量上限，执行仍受权限、队列和资源限制。
  3. 由平台管理员在可信服务器终端签发独立来源凭证；完整值只显示一次，有效期为 1–90 天。把它存入调用方后端的密钥管理，再注入环境变量 AWESOME_DEPLOY_TOKEN。不要通过聊天、Git 或前端交付。
  4. 从实际后端运行环境核验能访问平台 HTTPS 地址。若后端也运行在受限容器中，网络放行需按其运行外连策略单独配置；Token 本身不授予网络连通性。
  5. 待部署仓库应包含符合平台使用手册的 awesome.yaml 和部署所需文件。平台读取用户仓库并按原有业务代码部署，接入方不得假设平台会修改业务逻辑。私有仓库的读取权限由平台另行配置；自动化 API 凭证不等于 Git 仓库凭证。
awesome-deploy --config /etc/awesome-deploy/config.json api-token-create \
  --user-id MEMBER_ID --name group-web-backend --kind source --all-apps --days 30

如需撤销，管理员使用 api-token-list 找到凭证 ID，再执行 api-token-revoke --id CREDENTIAL_ID。撤销、过期或负责人失去权限后，凭证无法继续提交；已绑定该凭证的任务也无法再由它查询。轮换时应先处理未完成任务。

3. 平台 API 契约

方法与地址

作用

调用条件

POST /api/v1/automation/deployments

创建部署任务；成功受理返回 HTTP 202

Bearer Token、application/json、Idempotency-Key

GET /api/v1/automation/deployments/{id}

按任务 id 查询该次部署状态

必须使用提交该任务的同一枚 Token；GET 不创建任务

基础地址为 https://awesome.guanghexinzhi.cn。POST 请求体只接受明确字段：repository、ref、subdomain；更新已有应用时另加 appId。已有应用仍绑定域名时，仓库和域名前缀必须与该应用一致。域名前缀为 1–7 位小写字母、数字或中划线，并须与仓库中的配置一致。

{
  "repository": "https://github.com/your-org/your-repo.git",
  "ref": "main",
  "subdomain": "demo"
}

Idempotency-Key 必填，长度 1–128，只能含英文字母、数字、点、下划线、冒号和中划线。每一次真正的新部署使用新键；同一请求因超时重试时保持相同 Token、请求体和键。相同键配不同请求会冲突。将上面的 JSON 示例保存为 deployment.json，再运行下面的 curl 命令。

curl --request POST --fail-with-body -sS \
  -H "Authorization: Bearer ${AWESOME_DEPLOY_TOKEN}" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: group-web-request-001" \
  --data-binary @deployment.json \
  https://awesome.guanghexinzhi.cn/api/v1/automation/deployments

受理响应包含 id（部署任务编号）、appId（应用编号）、status 等字段。新应用在入队时即分配 appId；应保存这两个编号。此时通常是 queued，appId 存在也不代表已上线。后续更新该应用时在 POST 请求体中传回这个 appId。

curl --request GET --fail-with-body -sS \
  -H "Authorization: Bearer ${AWESOME_DEPLOY_TOKEN}" \
  https://awesome.guanghexinzhi.cn/api/v1/automation/deployments/JOB_ID

4. 调用方后端必须实现的流程

  1. 先验证自己网页的登录用户是否允许申请部署，再校验仓库、分支、域名前缀和已有 appId。不要把用户输入直接当作平台授权。
  2. 在自己的数据库先持久化申请记录、规范化请求体和幂等键，然后再发 POST。至少保存：本地申请 ID、申请人、请求体摘要、幂等键、平台任务 id、平台 appId、状态和更新时间。Token 只保存在密钥管理，不写入申请记录或日志。
  3. 收到 202 后持久化平台返回的 id 和 appId，再向网页显示“已受理/排队”；不要显示“部署成功”。
  4. 若 POST 超时或响应丢失，以同一 Token、同一请求体和同一幂等键重试，以取回同一个任务；不要直接换键，以免重复部署。
  5. 后台使用 GET 查询状态，并把结果写回自己的申请记录；网页只读自己后端保存的状态。可以按逐步延长的间隔轮询，避免浏览器关掉后失去追踪能力。
  6. 状态为 succeeded 时，再看 active 和 url；succeeded 说明该次任务曾成功，active 才表示它仍是当前在线版本。failed 时展示平台 error；recovery_required 时提示平台管理员核查，不得自动当成成功或盲目重试。

5. 飞书多维表格登记

平台已有独立同步进程，将所有平台应用记录和部署任务记录镜像到专用飞书多维表格；API 提交与网页提交走同一平台数据库，因此都参与同步。新应用在受理后可形成应用主表记录，部署任务形成部署记录表记录；负责人和提交人来自凭证关联的飞书成员。

多维表格同步是异步的，网络故障时会保留待同步项并重试；表格不是部署状态的权威来源，也不应成为对方后端判断成功的依据。对方后端应使用任务 GET 响应。同步内容不包含 Token、业务密钥、原始执行日志或错误详情。

6. 常见失败与处理

应检查什么

Bearer 凭证缺失、过期、撤销或格式错误

403

凭证范围、负责人的部署权限、目标应用权限；或误从其他网页 Origin 直接调用

400 / 409

幂等键格式、同键不同请求，或应用及域名冲突；以实际返回的错误内容为准

415 / 422

Content-Type 必须是 application/json；检查 JSON 字段、类型和取值

网络超时或 5xx

202

仅表示任务入队；继续 GET 查询，不应视为成功

自动化凭证当前只可提交部署并查询自己提交的任务，不能用来管理成员、修改业务密钥、下线应用或调用网页登录接口。若业务部署需要密码或外部 API Key，按平台现有密钥配置流程单独处理；不要放进仓库或部署请求。

7. 交付验收清单

□ 网页前端请求只到本项目后端；抓包和构建产物里均没有平台 Token。 □ 后端负责人、凭证范围、到期日和撤销方式已记录；实际运行环境可访问平台 HTTPS。 □ 首次 POST 返回 202、任务 id 和 appId；本地数据库在发请求前已保存申请与幂等键。 □ 同键同请求重试返回同一任务；真实新部署使用新键；更新已有应用传 appId。 □ 浏览器关闭或后端重启后仍能继续查询；queued/running/succeeded/failed/recovery_required 均有明确页面状态。 □ 成功时核对 active 与 url；失败时展示可行动的原因；飞书登记最终可查，但不依赖表格来判定部署成功。

8. 给开发者和 AI 的实施说明

请以本文的接口契约实现“同组网页后端发起并追踪 Awesome Deploy 部署”。先检查现有项目的身份、数据库和任务执行机制，沿用项目技术栈；实现后端持久化申请、签发的来源凭证安全注入、POST 提交、幂等重试、GET 后台查询、状态展示和必要的权限检查。不要把 Bearer Token 交给浏览器，不要直接修改 Awesome Deploy 或用户业务仓库来适配调用。以第 7 节逐项验收，并明确报告未能在目标环境实测的网络与凭证条件。

9. 平台不可达时的独立请求登记

如果同组网页需要在部署平台不可达时仍然保留上线申请，应把请求先交给运行在网页后端主机或其他独立主机上的接入服务。不要把接入服务和部署平台放在同一台故障主机。接入服务只有在本地 SQLite 提交成功后才返回 HTTP 202；同时同步尝试将完整、无秘密的部署请求写入专用多维表格「部署请求」。飞书写入失败不会阻止接入服务继续向可用的平台投递，恢复后会补写。

调用方提交一次请求到接入服务的 POST http://127.0.0.1:8099/requests，携带独立的 Bearer 接入凭证、Content-Type: application/json 和唯一 Idempotency-Key。请求体仍使用平台的 repository、ref、subdomain、可选 appId。接入服务返回的 requestId 是请求收据；此时 status=pending 仅表示已在独立接入端持久保存，不代表部署平台已接收。后端调用 GET /requests/{requestId} 查询后续状态；平台接收后才出现 jobId、appId，状态转为 submitted。

接入服务后台以原请求 ID 作为平台的幂等键自动投递并查询最终任务状态。平台断网或超时，服务会按有上限的退避继续投递；平台明确返回 HTTP 400、409 或 422 时则记录为 rejected，等待调用方修正请求后用新请求 ID 提交；即使第一次平台已接收但响应丢失，同键同请求也只取回原任务。调用方不需要自行猜测何时重试平台。接入服务重启会继续处理本地未完成项；本地库损坏或丢失时，可从多维表格恢复签名有效的记录，表中已记录最终状态的请求不会再次提交；若表中状态滞后、接入端本地库和平台数据库又同时丢失，不能仅靠表格保证恰好一次，应先恢复平台数据库备份再开放投递。Token、密码、业务密钥、原始日志都不能写进表格。

现有多维表格已新建独立的「部署请求」表（表 ID：tblgVwWTlwxvQ4Mv），字段为「请求 ID」「请求内容」「完整性签名」「状态」「部署 ID」「应用 ID」「提交时间」「更新时间」。原有「应用」和「部署记录」表仍只镜像平台结果，不能用作待投递队列。完整性签名由接入端保管的独立密钥生成，恢复时拒绝手工改写或签名不符的行；此密钥与接入端数据库都需要备份。若请求连独立接入端也未到达，网页后端必须先持久保存申请意图或明确告诉用户未受理，不能声称已登记。

独立接入服务的配置、部署方式、故障验收和表字段见项目仓库 docs/intake-relay.md。同组网页项目尚未确定，因此当前代码提供可部署的接入服务及协议，尚未接入具体网页后端，也未在另一台主机上线；在完成独立主机和表格配置前，仍按本手册前文的直接平台 API 流程使用。
