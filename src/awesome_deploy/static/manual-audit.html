1 目的、范围与生效边界

本协议规定提交一个服务上线时需要提供的材料、平台应完成的审计、管理员的批准条件，以及部署后的验证和留痕。适用于组织内部成员经网页或 Skill 提交的 GitHub/GitLab 项目，也适用于同一应用的后续更新。网页与 Skill 使用同一套服务端规则。

本文是内部工程协议的 v1 审查稿，日期为 2026-10-16（Asia/Shanghai），本次按审查意见补充发布有效性与消耗审计。正文中的“必须”“禁止”是拟议的实施要求；只有经过审查、形成不可变规则版本并完成平台接入后，才作为自动放行条件生效。本次交付只更新协议与报告格式，不修改当前平台行为，不表示任何服务已经通过审计或获准上线。

本文补充《Awesome Deploy 接入技术协议 v1.1》，不替代 awesome.yaml 的字段约束，也不授权为了适配平台而关闭鉴权、删除数据库、改写业务语义、伪造健康状态或替换成演示服务。确需改业务代码时，应另行确认业务变更并重新提交版本。

概念

含义与边界

预检

检查材料和配置是否满足进入后续流程的条件；不代表完整代码审计、生产批准或资源占用成功。

审计

按指定版本规则检查固定材料，形成带证据、覆盖范围和未验证项的结论。没有发现问题不等于不存在问题。

审批

具备权限的管理员对具体申请、报告和发布材料作出人工决定；审计通过仍须审批。

上线验收

确认批准的镜像及配置实际运行，候选健康、HTTPS 路由和必要业务检查符合预期。

操作审计

记录提交、审计、批准、部署、失败、回滚、下线等事实；运行日志不能代替审计报告和批准记录。

2 责任分工与提交材料

角色

责任

提交人 / 服务负责人

说明用途、数据、访问范围、外部依赖和恢复责任，提交真实仓库版本；存在计费或额度消耗时自行设计、实现并维护消费审计规则；处理审计发现并承担服务维护。

Skill / 开发 AI

协助形成声明、清单和自检证据；不得自行批准、伪造实测结果或覆盖平台规则。

平台审计执行器

从可信来源取得固定材料和目标环境证据，执行检查，保存正式报告；不接受客户端自填结论作为放行凭据。

管理员 / 审批人

核实报告与身份，批准或驳回具体申请；风险例外另行记载，不把失败检查改写成通过。

运维 / 数据责任人

维护服务器与密钥、完成备份恢复和故障处置，记录人工操作与资源归属。

建议默认提交人不得审批自己的申请。批准人必须来自平台维护的管理员身份映射，不能由请求体中的姓名或角色决定。仅有共享 operator Basic 账号时，只能确认账号层面的行为，不能证明实际员工或职责分离；启用正式审批门禁前必须接入可核验的个人身份。Skill 使用同一认证流程，报告中不得要求用户填写或粘贴访问令牌。

材料

最低内容

仓库与清单

规范仓库 URL、请求的 ref、平台解析的完整 commit；根目录 awesome.yaml；使用 build 时提供真实 Dockerfile、锁文件和离线依赖。

服务声明

负责人、用途、受众、哪些路径可匿名访问、认证与授权方式、数据类别、持久化需求、外部目标及用途、维护和恢复联系人；是否涉及大模型等计费或额度消耗，以及消费审计规则索引、费用责任人和明细查询方式。

身份与目标

可信提交人 ID；新建或更新、原 appId（若有）、目标环境、期望域名前缀；不能仅凭同一仓库认定应用归属。

变更说明

相比上个成功版本的功能、权限、路由、依赖、秘密引用、资源、存储和数据格式变化；部署封装不得偷偷改变业务行为。

验证与恢复材料

现有健康检查、关键业务与权限验证方法、实测结果及未测项；有数据时说明备份、恢复、格式兼容和可接受停机。

秘密与外联

只列配置名称、用途、归属及由平台读取的版本引用；外联列实际域名、协议、端口、数据类别和业务凭证责任，不含秘密值。

服务声明建议采用独立的 service-declaration.json 或平台表单记录，并计算内容摘要；它是拟议的审计输入，不是当前 awesome.yaml 的新字段。DEPLOYMENT.txt 沿用既有接入协议。用户声明是待核验材料，不能替代代码、测试或平台证据。没有持久存储、外部依赖或秘密时应明确声明空集合，不凭空添加功能。 消费审计规则作为服务声明及材料清单的一部分，使用 usageAuditPolicies 数组索引；每项含 policyId、version、ref、sha256、services，分别表示规则标识、版本、平台保存的受限不可变正文引用、正文原始字节摘要和适用服务名集合。ref/sha256 由平台固定材料时生成或核验；提交人提供规则正文或固定仓库文件位置即可，无需预先知道平台内部证据引用。明确无此类消耗时填 []，但该声明仍须经 AUD-013 核验；缺材料不能冒充不适用。

3 审计、审批与部署的顺序

阶段

动作与产物

允许继续的条件

A 接收与固定输入

验证身份、应用归属和仓库来源；解析 ref，固定 commit、生效配置、声明、秘密版本引用和目标策略。

必要材料可取得且可验证；新建申请先取得稳定 applicationRequestId。

B 源码与配置预审

审查业务逻辑、权限、秘密、构建文件及能力兼容；形成 stage=preflight 报告。

本阶段适用必检有效完成且 preflight 总体 pass；只允许进入受控构建，不能发布生产路由或接入生产卷。

C 受控构建与镜像审计

隔离构建；记录每个服务最终镜像不可变标识、依赖检查、来源关联及必要的隔离测试。

构建前后的材料与批准候选一致；形成 stage=release 报告，所有适用必检项有结论。

D 管理员审批

审阅 release 报告、未关闭风险和数据影响；绑定申请、报告摘要与材料摘要。

审批身份有效；无不可豁免阻断、未完成必检或无效证据；所需例外有效。

E 部署前复核

重新校验批准、材料、规则、应用当前版本、域名归属、容量与目标策略；再实际分配资源。

报告、批准及所需例外均有效，批准未撤销、报告未被正式替代，所有关键绑定一致；竞争或容量不足按失败处理，不能绕过。

F 候选启动与发布

存储身份核对、必要的旧版停机交接、启动候选、真实健康检查；然后切换路由并验证 HTTPS 实际上游。

候选健康通过后，在实际发布前再次执行第 6 节有效性复核；公开路由验证和规定的业务检查完成后才算上线验收通过。

G 归档与维护

保存验收、回收、回滚或需人工恢复结果，投递飞书摘要，记录后续下线和敏感配置变更。

只有确认清理才释放对应资源；结果不确定保留资源和恢复记录。

构建可以执行项目代码，必须在受限执行环境内进行，并限制网络、CPU、内存、磁盘、时间和工具权限；审计不能直接在管理员宿主环境执行仓库脚本。审批前的动态验证只允许隔离测试数据与测试凭证，不挂载生产卷、不向真实业务发送破坏性请求。缺少必要验证环境时记录未检查，不能用推测替代。preflight 的必检集合由平台按阶段生成，B 阶段检查不能遗漏；尚未产生的最终镜像检查属于 C 阶段，生产运行验收属于 F 阶段，均不能提前签为通过。

域名与端口预检只表示当时可用，不构成长期占用或上线承诺。端口实际绑定、容量和应用当前版本必须在 E 阶段重检；机器分配的候选端口记录在验收材料中，不能由客户端借此指定任意宿主机端口。

D 阶段批准的是后续受控发布操作，不能提前声称生产 HTTPS 已验收。F 阶段失败时依照既有恢复机制处理；持久数据回滚不自动撤销已发生的写入。必须保留操作证据，不能直接把数据库状态改成成功。

4 v1 最低审计规则

AUD-001 至 AUD-013 是发布审计的最低规则族。实际执行需按服务、路由和数据面展开检查实例，不能只检查一个服务后代表整个应用。覆盖集合由平台根据固定材料和规则集生成，客户端不得自行删减。无关规则可标为 not_applicable，但必须给出可核验理由；缺少扫描工具不属于“不适用”。

规则

检查与证据

处理要求

AUD-001 材料与归属

固定仓库、完整 commit、应用/环境、声明、生效清单、构建上下文及最终镜像；证明镜像与目标业务版本关联。

材料不一致、归属不明或用演示镜像替代业务：阻断。

AUD-002 平台与资源兼容

按本次能力/策略检查域名 1–7 位及禁词、支持字段、端口/路由、CPU/内存、构建和存储约束；记录预检与实际分配区别。

不支持能力、非法域名/字段或资源超限：阻断。

AUD-003 构建与容器边界

检查 Dockerfile、依赖来源、非 root、只读根、主机挂载/提权/隐式 VOLUME、构建网络及资源限制。

要求突破隔离、泄露主机能力或违反构建策略：阻断。

AUD-004 依赖与镜像

对实际部署镜像的依赖清单、已知漏洞、扫描覆盖、工具/库版本和扫描时间取证；仅基础镜像扫描不能覆盖业务层。

已确认 critical/high 问题：阻断；工具命中待确认则 review，不能直接声称已排除。

AUD-005 秘密与配置

检查代码、历史目标快照、构建材料、镜像和日志的秘密暴露；核对 secretRefs、业务 Key 与平台 Key 隔离、应用归属和版本。

真实秘密泄露、越权继承或借用平台凭证：阻断；发现后先按事件流程处置，报告仅留脱敏位置。

AUD-006 认证、授权与公开范围

按路由验证匿名、普通用户、其他用户和管理员的边界；检查对象归属、会话/写入保护及敏感操作。公开内容可匿名，但须声明且不暴露受限操作。

内部功能实际匿名可用、越权读写或管理接口泄露：阻断。

AUD-007 输入与危险操作

按业务面检查注入、路径穿越、任意文件访问、上传限制、服务端 URL 请求和危险命令；提供可复核位置或最小无害验证。

确认可造成越权、执行代码或敏感数据泄露：阻断；潜在问题未证实不得写成已复现。

AUD-008 外联与数据边界

将声明的外部目标/数据类别与实际冻结网络策略分开；验证业务 TLS、权限、目标可达性和凭证归属，记录传给第三方的数据范围。

依赖超出平台策略、未授权外传或关闭必要 TLS 校验：阻断；未知目标需补证。

AUD-009 持久化与数据恢复

核对 /data 逻辑计划、既有卷身份、新建卷验证要求、停机交接、数据格式兼容、备份责任及恢复证据。

复用身份不明、静默重建空卷、可能双写或破坏性迁移无可执行方案：阻断。

AUD-010 健康与关键业务验证

检查健康探针真实有效且无破坏性；在可行隔离环境验证关键业务、权限和外部依赖；列明生产阶段仍须验证的项目。

伪造健康、关键路径已知不可用：阻断；必需的隔离检查未做或失败原因不明：review。

AUD-011 日志与维护责任

核对脱敏、安全事件、错误可诊断性、负责人、容量与故障处置；有数据时明确数据保留和恢复联系人。

秘密/敏感数据直接写入日志：阻断；其他缺项按证据确定 medium/low 并人工复核。

AUD-012 审计过程可信性

审计环境权限、证据来源、规则覆盖、工具状态、AI 输入范围、个人身份、报告与材料绑定均可核验。

自填通过、篡改证据、规则被仓库覆盖、身份未验证或必检结果缺失：不得放行。

AUD-013 消耗与费用审计

存在大模型、短信、付费 API 等计费或额度消耗时，核验服务自定规则、请求地址、调用次数、费用、可信请求来源、持久记录及验证证据；覆盖重试、超时和异步调用。详见 4.1。

最低规则缺失或实现不满足最低要求：fail、hardBlock=true，不得豁免；严重性按已确认影响确定。尚未验证则 not_run/unknown，执行错误则 error。明确无此类消耗且有证据方可 not_applicable；费用待确认本身不是失败。

公网暴露与业务权限分开判断：demo.awesome.guanghexinzhi.cn 可从公网到达，并不代表所有路径都能匿名使用；“内部使用”声明必须有实际鉴权、授权或已验证的入口控制。管理平台的登录也不自动保护被部署的业务。

现有接入协议中的 public-https-v1 是地址/端口层面的固定策略，不是按业务声明的域名建立白名单。平台允许公网 IPv4 TCP 443，不等于业务只能访问声明的域名，也不等于业务 API Key、额度或 TLS 校验已通过。规则审计必须如实报告这种执行边界。

新建卷在批准前只有 app/service/storage.name/mountPath 的逻辑计划，实例 ID 和创建时间应为 null。平台创建后，必须在交给业务进程前核验驱动、选项、归属和新实例身份，写入验收记录并关联原计划；此补录不允许改变逻辑计划。复用卷必须在审计材料中记录既有实例身份，并在使用前复核；卷丢失或不符必须停止，不得自动创建空卷冒充。

持有不可替代业务数据的首次上线，须证明应用读写路径正确，并在隔离测试卷演练备份/恢复；更新需证明新旧版本的数据兼容性及可执行的备份恢复步骤。没有生产数据时不要求伪造生产备份，但必须说明首次备份的责任人和触发条件。仅用于缓存且确认不含唯一业务数据的目录，可用可复核的重建测试替代完整备份恢复演练；声明必须说明重建来源、步骤和可接受影响。混存业务数据、未结消费记录或无法证明可重建时，仍按业务数据处理；卷身份与归属检查始终保留。

4.1 消耗与费用审计的最低要求

服务涉及大模型、短信、付费 API 等计费或额度消耗时，服务负责人必须根据业务自行制定并实现消费审计规则。当前使用免费额度不能直接视为不适用。平台统一最低字段语义及验收要求，不强制统一代理、SDK 或存储产品。AUD-013 按有消耗的服务和调用路径展开；无此类消耗须结合配置、代码与依赖说明其不适用依据。

最低项目

记录与统计口径

请求地址

记录实际请求的协议、主机和接口路径；动态路径中的敏感信息脱敏。地址不得含 URL 用户密码、查询令牌；不保存 Authorization、API Key、完整提示词或请求/响应正文。供应商重定向或模型回退产生的新调用须可关联到实际目标。

请求次数

分别统计业务请求数和实际供应商调用尝试数。一次业务请求关联多个外部尝试；重试、并行调用、回退分别计次，失败、超时和取消仍保留尝试记录。流式响应的分块不算多个请求；日志重复上报按唯一事件 ID 去重，不合并真实重试。

费用情况

记录金额、币种、实际/估算/待确认状态及计算依据。未知金额填 null 并标为待确认，不能填 0；实际为 0 须有依据。估算说明计费数量、单价或价格版本；失败、超时不自动等于免费。各币种分别汇总；需要折算时说明汇率、时间与来源。

请求来源（谁发起）

从服务端认证或可信任务上下文取得稳定主体 ID，区分用户、服务账号、定时任务、匿名请求。异步调用同时保留原始发起者与执行主体。匿名应如实标记匿名及可追溯范围；IP、客户端自填姓名或共享 Key 名称不能单独证明真实个人。费用责任人与实际发起者分别记录，不能互相替代。

关联与持久化

记录时间、唯一消费事件 ID、业务请求 ID、结果状态及适用规则版本。明细可按日期、实际目标和发起者检索汇总。规则须说明持久存储、保留期限、访问权限、采集失败的告警与补记方式，避免重启或重复投递造成静默丢失/重复计费。

对账与更正

规则说明对账责任人和时间：有账单时与供应商账单核对；免费额度、自托管等无账单场景，按供应商用量、账户记录或可核验的计价/资源分摊依据核对，并说明证据与精度边界。更正保留原记录和关联关系，汇总按同一消费事件的最新有效费用计算，不把对账更正当成一次新调用。供应商只提供汇总账单时，说明分摊依据和精度边界，不能把无法确认的个人费用冒充精确实际值。

模型名、tokens、图片张数、短信条数、供应商请求 ID 等按业务计费方式补充，字段名称和存储实现可由服务自定，但必须能映射到上述口径。预算、限额和异常费用告警可以作为增强项；v1 不要求同步建设完整财务系统。

例：用户操作一次，首次调用超时后重试两次，记业务请求 1 次、供应商调用 3 次，各自记录结果和费用状态；首次超时费用未知时标为待确认。三次调用的日志分别重传，不增加调用次数。异步执行时不能只记录 worker 而丢失用户发起者。

最低验收以模拟供应商、固定账单样例或已获授权的隔离测试凭证覆盖正常请求、重试/并行、超时费用待确认、重复日志去重、异步来源传递、持久保存及脱敏；验证服务实现实际产生的记录，不仅检查提交人手填表格。无需为了通过审计产生真实付费调用。缺失最低规则、少计重试、未知费用记 0、伪造来源或泄露凭证均不得通过；明确标为待确认且有对账机制的费用，不因账单尚未到达而阻断上线。未适用的调用模式须有依据，不能虚构实测。

5 检查状态、风险等级与总体结论

检查状态 status

含义

pass

本检查实例在声明的范围内满足规则，并有证据。

fail

已确认违反规则，保留问题证据和处理要求。

warn

存在已说明的非硬阻断风险或未满足的规则要求，需按规则处置；单纯维护建议不使用 warn。

unknown

已检查，但证据不足或相互冲突，无法判断。

not_run

应检查但尚未执行，包括工具或隔离环境暂缺。

error

执行、取证或解析失败，不能产生有效结论。

not_applicable

基于实际材料确认该检查不适用，附理由和支持证据。

severity 表示风险影响：critical、high、medium、low、info、none。critical/high 用于已确认的严重影响；只有模型怀疑或扫描器原始命中时，先保留置信与证据不足说明，不能凭一个分数自动认定事实。priority 或“低优先级观察”不能替代严重性和规则判断。 已满足规则，仅有不影响放行的维护建议时，可记录 pass、severity=info，并在 summary/remediation 说明，不要求申请例外；不得借此把真实违规或未验证项降级。

总体结论 conclusion.result

聚合条件与下一步

block

存在已确认硬阻断或 critical/high 风险。停止本次发布，修改后重新审计。其他未完成项仍保留。

error

不存在已确认 block，但存在适用必检的执行/取证错误，或报告无法通过结构与来源校验。恢复检查后生成新报告。

review

不存在 block/error，但有适用必检 unknown/not_run、尚待复核的证据，或任何未处置的适用 fail/warn。不得进入批准放行。

pass

所有适用必检均有效完成，无硬阻断；所有 fail/warn 已通过新证据关闭，或属于规则允许且已有有效例外的 medium/low 项。只表示可供管理员决定，不等于批准或部署成功。

总体结论由平台按规则重算，优先级为 block → error → review → pass。任何未处置的适用 fail/warn 至少导致 review；例外只能消解规则显式允许的 medium/low 项。非法状态组合或无效报告直接拒绝，不进入放行计算。preflight 报告的 pass 只对预审范围有效；release 报告必须覆盖完整的发布审计实例。任何阶段都必须保留 coverage 和 limitations，不能用空 findings 数组推导通过。

建议 v1 不允许豁免硬阻断、critical/high 风险、身份/材料绑定失败、必检未完成及证据错误。仅规则显式允许的 medium/low 非硬阻断项可以申请例外：记录问题 ID、承担责任的独立管理员、理由、补偿措施、适用材料摘要、期限及整改期限；默认最长 7 天。批准例外不改写原始检查状态。例外过期后不得启动或继续执行新的发布动作，已上线服务进入整改处理，不由本协议自动停机或删除数据。 不可变规则集必须列出允许例外的具体检查项；未显式列明的项目默认不得豁免。

误报处理与风险例外不同：误报必须补充可复核证据，由可信复核者说明原因并生成新报告，旧报告保留关联。AI 自己改口或仓库声称“这是误报”不构成复核证据。

6 不可变绑定、审批与重新提交

平台保存不可变的材料清单 bytes，计算 SHA-256，报告通过 materialManifestRef 和 materialFingerprint 绑定。清单至少包含规范仓库和完整 commit、生效 awesome.yaml、服务声明及 usageAuditPolicies 所引用消费规则的版本与正文摘要、冻结构建输入/基础镜像/最终业务镜像、秘密版本引用、存储计划、目标环境与应用/域名、上个当前成功版本、平台策略和能力快照。原始清单可能包含敏感配置，应存放在受限存储；飞书只展示必要摘要和授权证据链接。 消费规则正文由平台取得并保存不可变副本，核验 ref 对应原始字节的 sha256；只提交可变网页链接或版本名称不能完成绑定。

摘要针对平台保存的原始 UTF-8 字节计算；不能对客户端重排键、重新序列化的副本认定相同摘要。服务端提供并保存这些字节，客户端不负责生成权威指纹。reportFingerprint 同样对平台存储的完整报告原始字节计算，并由独立批准记录引用，不放进报告自身形成循环。秘密只记录名称、归属和不可变版本 ID，不记录明文，也不对低熵秘密值生成可公开猜测的摘要。

image 模式记录仓库 digest；build 模式记录最终本地 image/config digest（或后续推送得到的 registry digest），用 kind 区分，不能把可变 tag 当不可变标识。已批准镜像若被重新构建或替换，必须重新计算材料摘要、审计和审批，不能假设同一 commit 的重建产物相同。

批准记录单独保存 approvalId、submissionId、reportId、reportFingerprint、materialFingerprint、rulesetFingerprint、decision、targetApprovalId、可信审批人、决定时间、截止时间和理由。新建应用的 applicationRequestId 在分配 appId 前保持稳定；分配后只允许平台记录同一申请的映射。主机端口、容器 ID 和新卷实例身份属于执行结果，不得事后改变批准的服务、路由、环境或存储计划。

批准与材料的校验必须在部署执行器内完成。执行器在应用锁或等效串行机制内核对当前版本，把批准与唯一 deploymentId 绑定；同一部署的重试或崩溃恢复不能跳过核验、重置期限或复用已失效授权。除 E 阶段外，每次实际切换正式流量前，必须再次核验报告及批准尚未过期、批准未撤销、报告未被正式替代、无新阻断、所需例外仍有效，且材料、规则、目标环境和应用当前版本一致。撤销、正式报告替代与发布授权判定须按同一应用串行处理；先已生效的撤销或替代必须阻止本次发布。其他申请不得重放批准；客户端、Skill 或飞书记录中的 approved=true 都不是授权凭据。

建议默认：release 报告以 completedAt 起算、批准以 decidedAt 起算，各自默认有效 24 小时；E 阶段和实际发布前均须满足当前时间早于二者 validUntil，所需例外也须未到期，实际截止取最早者。漏洞库等时效证据须记录版本和时间，正式批准前更新到 24 小时内，并满足发布时规则集要求的证据时效。材料不变时可复用已核验的静态证据，仅刷新有时效性的扫描、策略和目标环境证据，形成新报告并重新审批，无需每日全量重复检查。发布后的验收跨过截止时刻，不追溯否定发布时有效的授权，但仍须完成实际验收；如需再次切流则重新核验。报告/批准失效不等于立即终止既有线上服务。

代码、配置、声明或消费审计规则、镜像、秘密版本、存储逻辑计划、目标环境/应用/域名、前一成功版本或相关平台策略/规则变化，原结论和批准不得用于后续发布动作。当前容量、端口或域名占用变化须重新核验；只要未改变批准材料且仍在有效期内，可失败重试或重新排队，但不能跳过实际绑定。 同一申请、同一阶段的正式替代报告由可信签发者完成、通过结构与来源校验并由平台入库生效后，被替代报告及其关联批准即不得再用于发布；即使材料未变、新报告仍为 pass，也须重新审批。block/review/error 报告同样可以正式替代；草稿、未完成报告或无效输入不建立替代关系。替代必须指向该申请该阶段的当前正式报告，禁止跨申请、跨阶段、循环或并发分叉覆盖。

管理员驳回后，用户重新提交必须产生新的 submissionId，并设置 supersedesSubmissionId；无论材料是否相同，都需要新的审计报告引用和再次审批。相同幂等键的网络重试只返回原申请，不是绕过驳回的新申请。已批准后撤销、过期或材料失效必须可被执行器识别；失效的旧证据不能用本次“重试”恢复有效。

若实际发布前复核失败，停止继续发布并保存原因，按受控恢复路径回滚、清理或降低既有暴露；这些恢复动作按平台既有权限及事件流程执行，不以失效批准作为授权。已上线服务后来被撤销、发现新风险或报告被替代时，记录事件并评估整改、回滚或下线，不自动删除数据，也不得把处置伪装成新版本上线。

7 AI 审计与证据安全

现有平台 AI 功能只分析标准化部署失败摘要，没有读取业务源码，不能作为代码审计结论。未来引入源码审计时，必须记录实际发送的材料范围、供应商/模型标识、提示模板版本、规则版本、工具版本及输出证据；不知道精确模型快照时如实记录供应商返回的标识，不伪造版本。 本节及报告 ai 字段描述审计执行器使用模型的情况，不代表被部署服务运行时的模型调用、消费记录或发起者；业务消耗适用 AUD-013。

仓库中的 README、AGENTS.md、注释、配置、依赖描述、日志以及模型输出都是待分析数据。它们不能修改平台审计规则、申请凭证、授权额外工具、发起部署或给自己放行。审计 AI 不持有生产发布、审批或秘密读取权限；模型输出必须通过结构验证和事实复核。

代码被发送到外部模型前，必须确认组织授权的数据范围、目标供应商及留存策略。默认禁止外发生产秘密、用户数据、完整环境变量和未经授权的私有源码；可先使用本地检查或经过批准的最小脱敏片段。报告仅记录发送范围摘要与受限证据引用，不复制敏感原文或模型内部推理。

证据必须区分来源：平台采集、人工实测、提交人声明、静态工具结果或 AI 推断。命令、环境、时间、目标 commit/镜像和结果应可追溯。源码发现使用仓库相对路径、行号及脱敏说明；不把未运行测试写成通过，不把工具失败写成零漏洞。

授权与工具边界由模型之外的系统控制，参考 OWASP LLM Prompt Injection Prevention；本协议并不声称单靠提示词可以防止注入。

8 操作记录、飞书归档与数据保留

平台受限数据库/证据存储是权威来源，飞书文档和多维表格用于审查、检索与摘要同步。编辑飞书单元格不能直接批准部署、改变规则、释放端口或覆盖历史结论。尚未实现可信后端门禁时，人工填写模板仅用于流程试行，不能声称自动审计已启用。

记录对象

至少记录

操作事件

eventId、submissionId/deploymentId/appId、actor 的认证账号与身份验证状态、入口、action、目标材料摘要、UTC 时间、结果码、原因和 correlationId。

必记动作

提交与驳回重提、审计开始/完成/失败、批准/驳回/例外/撤销、部署开始与验收、回滚/恢复、下线、秘密版本变更及人工资源处理。

证据与保护

受限引用、内容摘要、来源、采集时间及脱敏标记；读写分权，修正采用追加记录。普通应用日志和单机摘要链不能被宣称为绝对不可篡改。

飞书摘要

服务/申请/版本、负责人、审计结论、严重性计数、批准状态、部署结果、未验证项和权威记录链接；不同步秘密或完整源码。

建议默认保留：审计报告、批准、例外和操作事件不少于 180 天；脱敏详细证据不少于 30 天。仍被当前运行版本、未结事项或事故调查引用的记录继续保留，不能到期直接删除。涉及用户或业务数据的留存按组织要求另行确认，不把这些建议天数当作法律要求。

业务消费明细由服务按其消费审计规则持久保存并受限查询；飞书仅按需同步按期汇总、待对账状态和受限查询入口，不要求同步每笔消费、完整提示词或敏感身份信息。上述 180/30 天是平台审计记录的建议值，业务消费明细的保留期限、未结费用继续保留和更正机制须在服务规则中明确。平台 AuditEvent.actor 是部署操作人，消费记录中的发起者是实际业务来源，二者不能混用。

关键放行记录无法持久化时，不得开始新的上线或下线操作；异常处置仍应允许按受控恢复路径降低风险并补记。飞书同步失败只进入重试队列并提示，不回滚已正确提交的部署，也不能丢失平台权威记录。

应用下线与删除持久数据/秘密是不同动作。下线后应记录保留对象及责任人；清理数据须另行核对权限、归属、依赖和备份，不能因为域名被再次分配就转交旧数据或秘密。

日志中排除秘密并限制读写、记录事件关联与检查日志完整性的设计参考 OWASP Logging Cheat Sheet。具体保留期是本协议建议值。

9 审计报告格式 v1：字段与约束

报告采用 JSON 对象，reportVersion 固定为 "1.0"。下表是拟议的序列化契约，不是当前平台已提供的 API。字段名区分大小写；时间使用带时区的 RFC 3339 字符串，机器记录统一 UTC；ID 是服务端生成的非空字符串；摘要为 sha256: 加 64 位小写十六进制。正式报告只追加，不原地改写；复核生成新 reportId 并引用 supersedesReportId。

字段

类型 / 必填

定义

reportVersion / reportId / stage / isExample

string / string / enum / boolean；必填

stage=preflight|release；isExample=true 的示例永远不能用于放行。正式记录必须 false。

submissionId / supersedesReportId

string / string|null；必填

关联本次申请；首份报告 supersedesReportId=null。后续指向同一申请、同一阶段的当前正式报告；正式替代及旧批准失效按第 6 节执行。

policy

object；必填

policyId、version、rulesetFingerprint；由平台加载的不可变规则集决定。

subject

object；必填

见下方材料绑定结构；不能只提供仓库分支或应用名字。

object；必填

requester={accountId,identityVerified,channel}，channel=web|skill|operator；issuer={kind,id}，kind=platform_auditor|human_reviewer，正式 issuer 经平台验证。

datetime；必填

object；必填

checks

array；必填

每个检查实例的状态、证据、严重性和处理建议，见后文。不能以空数组表示全通过。

array；必填

object；必填

subject 必填：applicationRequestId、appId（尚未分配时 null）、environmentId、repository、commit、subdomain、previousReleaseId（首次为 null）、declarationFingerprint、effectiveManifestFingerprint、materialManifestRef、materialFingerprint、images、secretVersions、storagePlan、targetProfile。release 报告的 images 必须覆盖每个实际服务；preflight 可为空，但不能因此产生生产批准。commit 必须是平台已经解析的完整对象 ID，不能是 main/latest 等名字。

images[]={service,kind,digest}，kind=registry_manifest|local_image_config。secretVersions[]={service,name,versionRef}，versionRef 由平台读取且可核验，不是秘密内容。storagePlan[]={service,name,mountPath,mode,expectedIdentity}，mode=create|reuse；create 的 expectedIdentity=null，reuse 必须记录 volumeId、instanceId、createdAt。targetProfile={platformVersion,capabilitiesRef,capabilitiesFingerprint,observedAt,networkPolicyId,networkPolicyFingerprint}；来自目标平台，不由提交人自填。

消费审计沿用现有 checks/evidence，不新增一套业务账本：checks 使用 AUD-013 及实际服务/路径 scope；evidence 保存规则核验、模拟或隔离测试记录和脱敏明细样例。规则索引 usageAuditPolicies 按第 2 节保存在服务声明与不可变材料清单中，由 subject.declarationFingerprint 和 materialManifestRef/materialFingerprint 绑定；人工报告从已核验清单展示 policyId、version、sha256 和适用服务。规则变化必须重新审计和审批。持续发生的消费明细不写回已完成的上线报告，也不复用报告 ai 或平台 actor 字段。

checks[] 必填：checkId、ruleId、scope、status、severity、hardBlock、summary、evidenceIds、remediation。scope={service,path}，应用级或非源码项可用 null。条件字段：not_applicable 必须有 applicabilityReason 及证据；unknown/not_run/error 必须在 summary 解释原因；error 必须有脱敏 errorCode。hardBlock 由规则与已确认事实计算，客户端不可自行降级；只有 fail 可以使 hardBlock=true。fail 的 severity 必须为 critical/high/medium/low，warn 必须为 medium/low；pass 可以为 none/info；其余状态必须为 none，潜在影响写在说明中。critical/high 的 fail 必须 hardBlock=true。非法组合拒绝。

evidence[] 必填：evidenceId、type、source、ref、sha256、collectedAt、redacted。type=source|config|tool_result|test|runtime|statement|ai_output；source 指真实采集器或可信人工身份；ref 指向平台受限证据，不接受可随时替换的任意公网链接作为唯一依据。statement/ai_output 本身不能证明动态验证通过。

可选 findings 不另设一套冲突结构：有问题的 checks 就是发现清单；多处不同证据使用不同 checkId，例如 AUD-006:web:/admin。汇总计数由 checks 按状态/严重性计算，避免手工计数与正文矛盾。未知 reportVersion、重复 ID、缺字段、无效枚举、引用悬空、覆盖缺项或总体结论不一致，服务端必须拒绝；空集合与 null 必须按上文语义使用。

10 批准记录与部署验收记录格式

批准和部署验收是独立对象，不在已完成的审计报告中追加一个可被随意修改的 approved 字段。三者通过申请、报告和材料摘要关联。以下字段均为拟议协议，未代表新增 API 已实现。

对象

必填字段与条件

ApprovalDecision

recordVersion="1.0"；approvalId、targetApprovalId、submissionId、reportId、reportFingerprint、materialFingerprint、rulesetFingerprint、decision=approved|rejected|revoked、actor={accountId,identityVerified}、decidedAt、validUntil、reason、exceptionIds。每条决定使用新的唯一 approvalId；approved/rejected 的 targetApprovalId=null。revoked 的 targetApprovalId 必须指向原 approved 记录，并与其 submissionId、reportId、reportFingerprint、materialFingerprint、rulesetFingerprint 一致；不得指向自己、驳回或撤销记录。所有决定均须可信且有相应权限的个人身份；approved 的 decidedAt<validUntil，rejected/revoked 的 validUntil=null。撤销追加记录，不修改或擦除原批准；执行器按 targetApprovalId 识别原批准失效。

DeploymentAttestation

recordVersion="1.0"；attestationId、deploymentId、submissionId、approvalId、reportId、materialFingerprint、applicationMapping、observedImages、observedVolumes、allocatedPorts、publication、requiredCheckIds、checks、evidence、result、startedAt、completedAt、eventsRef。publication={authorizationCheckedAt,publishedAt,evidenceIds}；时间未知或未执行为 null，未产生证据为 []。记录本次最终发布尝试，全部尝试留在 eventsRef；首次 appId 和卷身份在此保存实测映射。

验收 checks 与 evidence

验收 checks 必须覆盖材料一致性、批准/策略有效性、资源和卷身份、候选健康、HTTPS 上游验证、关键业务验证；每项检查记录 checkId、status、summary 与 evidenceIds。沿用第 5 节状态枚举；平台生成 requiredCheckIds，覆盖不得遗漏。不适用必须有理由和证据。evidence 沿用第 9 节结构，独立保存运行阶段新证据，不能补写旧审计报告。

验收 result

succeeded|failed|recovery_required。仅候选启动成功不能标 succeeded；已切路由但尚未验收不属于最终成功，应保留执行中状态。

AuditEvent

eventId、action、actor、channel、occurredAt、submissionId、deploymentId/appId（未知为 null）、materialFingerprint、resultCode、reason、correlationId。批准/撤销相关事件另须 approvalId、targetApprovalId，并与对应 ApprovalDecision 一致；其他事件二者为 null。人工恢复同样记录身份与依据。

验收中 observedVolumes 记录 service、storage.name、volumeId、instanceId、createdAt、identityCheck；observedImages 与批准 digest 按 kind 一致比较。首次创建从 storagePlan 映射到实际身份；复用严格匹配 expectedIdentity。所有 evidenceIds 必须能在本验收 evidence 中解析并验证。只有全部适用必检 pass 或经证据确认的 not_applicable 才可 succeeded；fail/warn/unknown/not_run/error 均不可成功。批准只涉及本申请和本次部署，禁止把测试环境报告用到生产、把原应用批准用到新应用或用同域名历史记录继承旧数据。 验收不复制原审计报告中已接受例外的 fail/warn，而是核验这些例外在发布时仍有效；不能用例外放宽候选健康、HTTPS 或关键业务的实际故障。succeeded 必须有 publication 的两个时间及有效证据，startedAt≤authorizationCheckedAt≤publishedAt≤completedAt，且 publishedAt 早于报告、批准和所需例外的截止时间。批准/策略验收应引用实际发布前复核证据；仅因验收完成时自然到期不倒推为失败，验收中发现新故障或新风险仍须处理。

approved 记录只有当前正式 release 报告 pass、例外在有效范围、材料与规则一致且无新阻断时才可产生；审批被撤销、过期、报告被正式替代或新规则要求重审时，不得启动或继续新的发布动作。批准记录落库、执行器占用及失效状态判断须防重放；同一申请的网络重试可幂等，但不能复制 approvalId 触发第二次独立发布。再次审批生成新的批准记录；原部署的失败与恢复记录继续保留，不允许重写为已批准成功。

结论摘要

报告编号、协议/规则版本、服务与目标环境、审计阶段、总体结论、是否为示例。

发布材料

仓库、完整 commit、应用/域名、生效配置与材料摘要、每服务镜像、秘密版本引用和存储计划；从绑定材料展示消费规则标识、版本、摘要及适用服务。

覆盖与问题

适用检查数量、已检查/未检查/错误数量；按阻断、待复核、已接受例外排序列出证据、位置、影响和整改建议。

证据边界

实际使用的工具与时间、审计 AI 输入范围、未验证项、缺失信息；AUD-013 展示四项最低口径的验证结果、待对账边界及脱敏样例引用，不粘贴秘密或完整消费明细。

批准与执行

单独展示批准人/结论/期限/理由；上线后再关联验收与回滚记录。禁止预填“审批通过”。

填写示例：若 /admin 声明只允许管理员，但匿名实测可访问，应生成 AUD-006 对应实例 fail、严重性及 hardBlock，并附脱敏请求结果；总体 block。若没有完成匿名测试，应填 not_run 或 unknown，总体 review，而不是“未发现越权”。若是无存储静态站点，AUD-009 可在核对代码与清单后填 not_applicable，并附依据。
