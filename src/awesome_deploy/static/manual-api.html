Awesome Deploy｜自动化部署 API 使用手册

这份手册面向脚本、CI 和同组网页项目的后端，适用平台 0.11.2，核对日期 2026-10-23。普通自动化凭证用于提交部署和查询由同一凭证创建的任务；同组委托链路另提供按实际登录人权限搜索项目。完整仓库与清单要求见部署接入技术协议 v2.0。Token 必须保存在后端密钥配置中，不能放进网页 JavaScript；当前接口不开放跨站浏览器调用。

最重要的两点：HTTP 202 只表示任务已进入队列，不表示上线成功。完整凭证只显示一次，不要写进 Git 仓库、请求文件或聊天消息。

1. 取得 API 凭证

打开 API 凭证页面，使用飞书登录。在“创建个人凭证”中填写名称、部署范围和有效期；创建时需要最近 10 分钟内的登录确认。凭证有效期为 1–90 天，默认 30 天。

范围可选“我有权部署的应用”（可创建新应用并更新当前有权限的应用）、“指定单个应用”（只能更新该应用）、“仅创建新应用”。创建后立即复制完整凭证，存入调用程序的密钥配置，并以环境变量 AWESOME_DEPLOY_TOKEN 注入。页面之后只能查看凭证名称、范围和有效期，不能再次查看完整值。

少数具名自动化来源由平台管理员单独签发和撤销，并关联一位负责的飞书成员。来源可连续提交多个应用和任务；队列、权限及资源配额照常生效。

2. 首次部署

先在调用程序工作目录创建 deployment.json，将仓库和项目名称换成真实值。项目名称仍通过 subdomain 字段提交：1–7 位小写字母、数字或中划线，首尾为字母或数字，不含中文、空格或大写字母。ref 可省略，默认 main；需要其他版本时显式传入真实存在的分支、标签或完整 commit。仓库根目录必须有符合技术协议清单示例的 awesome.yaml，且 app.subdomain 与请求一致；构建文件也必须推送到同一版本。

{
  "repository": "https://github.com/your-org/your-repo.git",
  "ref": "main",
  "subdomain": "demo"
}

提交部署使用 POST /api/v1/automation/deployments。请求体是 JSON，需带 Bearer 凭证、Content-Type: application/json 和 Idempotency-Key。确认运行环境已从安全配置注入 AWESOME_DEPLOY_TOKEN；每次新的部署使用新幂等键，示例键仅作演示。

curl --request POST --fail-with-body -sS \
  -H "Authorization: Bearer ${AWESOME_DEPLOY_TOKEN}" \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-initial-001' \
  --data-binary @deployment.json \
  https://awesome.guanghexinzhi.cn/api/v1/automation/deployments

成功受理时返回 HTTP 202，包含任务编号 id 和应用编号 appId。两者都应保存；appId 已分配不代表应用已上线。status、phase 是任务状态与阶段；仅当该次成功部署仍为当前在线版本时，active 才为 true，url 才有值。

3. 查询任务结果

查询任务进度使用 GET /api/v1/automation/deployments/{JOB_ID}，JOB_ID 是提交响应中的 id。此普通自动化接口必须使用提交任务的同一枚有效凭证；同一账号另建的新 Token 不能查询旧凭证的任务。同组共享会话链路使用 GET /api/v1/integrations/deployments/{JOB_ID}，允许同一来源的有效委托凭证查询本来源任务。两种接口返回相同进度结构，GET 不创建或重试任务。按 pollAfterSeconds 轮询，terminal=true 后停止；调用方等待超时不等于平台任务失败。

curl --request GET --fail-with-body -sS \
  -H "Authorization: Bearer ${AWESOME_DEPLOY_TOKEN}" \
  https://awesome.guanghexinzhi.cn/api/v1/automation/deployments/JOB_ID

字段

含义

id / appId

本次任务 ID / 应用 ID；不要混用。

status / statusLabel

机器状态码 / 中文说明；queued、running 表示未结束；succeeded、failed、recovery_required、cancelled 是终态。

phase / phaseLabel

当前阶段码 / 中文说明，如 build / 构建镜像、health / 健康检查。阶段耗时不固定，不返回虚构百分比。

terminal

布尔值；true 时停止常规进度轮询，不代表部署成功。

createdAt / updatedAt

Unix 时间戳，单位秒，number；用于显示提交与最近更新时刻。

pollAfterSeconds

建议下次查询间隔：进行中为 5，终态为 0。查询失败可退避；调用方等待超时不等于任务失败。

error

部署失败或待恢复的中文安全诊断对象；无错误时为 null。不包含密钥或原始日志。

active / url

仅该成功版本仍为当前在线版本时 active=true 且 url 非空。历史成功不等于现在在线。

{
  "id": "任务编号",
  "appId": "应用编号",
  "status": "running",
  "statusLabel": "执行中",
  "phase": "build",
  "phaseLabel": "构建镜像",
  "terminal": false,
  "pollAfterSeconds": 5,
  "createdAt": 1792713600.0,
  "updatedAt": 1792713615.0,
  "error": null,
  "active": false,
  "url": null
}

status

含义与下一步

queued

已入队；稍后用同一接口查询。

running

正在执行；继续查询。

succeeded

该次部署成功；再看 active 和 url 确认它是否仍是当前在线版本。

failed

部署失败；查看响应中的中文 error，修复原因后用新幂等键重新提交。

recovery_required

需要平台管理员检查资源与恢复状态；不要把它当成成功。

4. 更新已有应用

同组共享会话链路支持 POST /api/v1/integrations/apps/search，专用委托来源凭证配合有效 sessionId，按实际登录人的部署权限搜索。A 本机适配服务对应 POST /apps/search；返回 appId 后可调用更新部署。普通 personal 或未启用委托的 source Bearer 不开放应用搜索。控制台仍通过网页登录会话 GET /api/v1/apps 后本地筛选。完整调用样例见同组后端实施手册第 2 节。

更新仍使用 POST /api/v1/automation/deployments，并加入已有应用的 appId，repository 须与该应用一致，当前已绑定域名的 subdomain 也须一致。保留数据下线且已释放域名的应用，可填新的空闲前缀，但仍须与新版本 awesome.yaml 一致。ref 省略时默认 main，也可显式更换为其他版本；真正的新部署使用新幂等键。创建新应用时不填 appId；失败后若要继续使用已分配的同一应用，也应传回该 appId，并确保凭证范围允许更新。

{
  "repository": "https://github.com/your-org/your-repo.git",
  "ref": "main",
  "subdomain": "demo",
  "appId": "已有应用编号"
}

“指定单个应用”范围的凭证只能更新那一个应用；如果账号失去该应用的部署权限，凭证也不能继续部署它。

5. 重试与常见错误

提交后未收到响应时，任务可能已经入库。保留原请求并使用相同请求体、相同凭证、相同幂等键重试，平台返回同一任务的当前状态，不新建任务。幂等范围绑定凭证，换 Token 或换键可能生成新任务。真正的新部署才换键；同键对应不同请求返回冲突。幂等键长度为 1–128，仅用字母、数字、点、下划线、冒号和中划线。

HTTP 状态或现象

处理方式

400

检查 Idempotency-Key 是否缺少或格式不合法。

401

检查 Bearer 凭证是否缺少、过期、被撤销或绑定身份已失效；不要使用网页登录 Cookie 代替。

403

检查凭证范围、负责人权限及应用权限；浏览器跨站调用也会被拒绝，应从同组项目后端调用。

404

检查任务 id 是否存在及接口路径；不要把 requestId、appId 当作任务 id。

409

检查幂等键是否复用于不同请求，或应用、域名及当前操作是否冲突；结合 error.code 处理。

415

请求须带 Content-Type: application/json。

422

检查 JSON 字段、类型、仓库、ref 和域名前缀格式。

网络超时 / 5xx

不能据此认定任务未创建；保留原请求、凭证和幂等键，按退避策略重试。

API 凭证不能用于网页管理、修改密钥、管理成员或下线应用。撤销凭证后，调用方不能再提交或查询；尚未执行的关联部署也会失去授权。查看凭证或撤销凭证请回到 API 凭证页面。

若任务因缺少登录密码或供应商 API Key 失败，到控制台相应任务补充配置；不要把秘密值加进部署 JSON。API 提交与网页提交一样，由后台异步同步应用及部署记录到飞书多维表格；表格写入成功不是 202 的前置条件，也不等于部署成功。

平台不可达时的请求收据

平台受理事务完成后即有任务记录，即使客户端没收到 202 也可能已入队；完全没收到的请求则不会由 B 留下记录。0.11.0 提供同组 A 端适配服务：先在本机 SQLite 保存申请并返回 requestId，再以来源凭证和签名身份凭据向 B 投递。它与 B 暂时同机，可应对 B 进程故障和响应丢失；整机故障仍需要异机备份。该链路使用 /api/v1/integrations/deployments，不改变本文原有 /api/v1/automation 接口。具体 A 项目尚未接通。

新的共享会话、A 端接口、可靠投递与迁移说明见 同组网页项目接入 Awesome Deploy API｜后端实施手册 第 1—6 节。Redis 保存登录态，数据库保存申请；此方案不将签名受理凭据写入飞书。原有应用和部署记录表在 B 收件后异步同步；旧独立登记模块的部署请求表恢复未自动接入此链路。
