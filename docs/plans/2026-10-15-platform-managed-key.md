# Platform-managed encryption key implementation plan

**Goal:** The user sets the application's login password. The platform generates and retains the encryption key without asking the user to copy it or confirm retention.

**Architecture:** Extend the authenticated configuration completion flow introduced in 0.6.0. Treat only the verified convention `secretRefs.MASTER_KEY: MASTER_KEY` (and no additional uses of that reference) as a platform-managed 32-byte / 64-hex key. Server-side generation occurs only on an authorized save for a fresh scope, under the existing worker lock, ownership checks, SQLite transaction and atomic create-only secret store. Existing keys are reused and never exposed or regenerated. A missing key for an existing application requires recovery of its original configuration. No customer source or manifest is modified.

**Stack:** Python/FastAPI, SQLite, private versioned files, browser JavaScript.

## API

GET/POST `/api/v1/deployments/{job_id}/secrets` retain the existing response and add `managed: boolean` to each item. The browser sends only user-supplied missing fields in `values`. A managed missing key with `canGenerate: true` is generated by the server during POST; `canGenerate: false` requires recovery, and configured values are preserved. Explicit client submission of managed values is rejected with a fixed Chinese diagnostic. Values never enter response metadata, browser storage, logs, AI requests or the source repository.
